# Helgrind: Norse-Themed Action-RPG

Helgrind is the working title for the badge's second native game, filling the "HELGRIND" menu tile (`kScreenHelgrind`, `firmware/src/screens/HelgrindScreen.{h,cpp}`) that has stood as a "game coming soon" placeholder since the [Doom removal](doom.md). Development started on the `helgrind_game` branch (created 2026-09-19, off `main`@`ac06a54`, the commit that landed [Vectortank](vectortank.md)'s opponent/pause-menu/spawn-radius work) as a from-scratch build rather than an evolution of the placeholder's static message. This page is a live design doc, not a record of shipped behavior — the "Design pillars" and "Confirmed design decisions" sections are the brief; the "First playable slice" section below describes what is actually built.

## Design pillars set at kickoff (2026-09-19)

- **Theme**: vaguely Norse fantasy — no specific mythology commitment yet (see open questions below).
- **Mechanical philosophy**: no novel gameplay mechanics. The brief is explicitly to draw from "the classic era of gaming appropriate for a monochromatic screen" — i.e. genre conventions from 1-bit/limited-palette handhelds and early consoles, not new systems invented for this game. This mirrors [Vectortank](vectortank.md)'s own precedent of leaning on well-understood arcade tricks (painter's-algorithm occlusion, billboard sprites) rather than novel rendering — Helgrind extends that "classic-era, budget-appropriate" philosophy from rendering into game design itself.
- **Minimap tied to the LED matrix**: the badge's ambient 8×8 IS31FL3731 LED matrix (`LED_MATRIX_WIDTH`/`LED_MATRIX_HEIGHT` = 8, `firmware/src/hardware/EchoDefines.h`) — the same secondary display [Vectortank](vectortank.md) claims for its radar via `LEDAppRuntime::beginOverride()`/`endOverride()` — is the minimap surface: one discrete room maps to exactly one LED pixel (see "World layout" below), not a compressed/zoomed view of a larger world.
- **Player representation**: the player renders as a single solid (always-on) pixel on the minimap.
- **Active quest indicator**: the map location of the currently active quest blinks at 1Hz on the minimap — the same LED matrix surface, distinct from the player's steady pixel.
- **Story shape**: described by the brief as "a dry series of collect the artifacts in the right order to unlock the main story quest" — i.e. a linear/gated fetch-quest chain is the primary story structure, not a branching narrative. Artifact categories named so far: weapons, amulets, and scrolls.
- **Inventory**: small (exact capacity not yet set).
- **Controls**: `a` opens the game menu, `b` is action/attack with the currently selected weapon, `y` is a special action (distinct from the weapon action), `x` cycles/opens weapon select. This reuses the badge's existing 4-button semantic layer (`Inputs::ButtonStates` — `a`/`b`/`x`/`y`, aliased over the same physical up/down/left/right buttons documented on [Vectortank](vectortank.md)'s control-scheme section) rather than inventing new input plumbing.
- **Footer**: the OLED screen footer shows basic game/player state, the same "status band along `OLEDLayout::kFooterTopY..kScreenH`" convention [Vectortank](vectortank.md)'s `drawVectortankFooter()` established (FPS/compass/HP there; Helgrind's is `drawFooter()`, described under "First playable slice" below).

## Confirmed design decisions (interview, 2026-09-20)

The design pillars above were the kickoff brief; this section is what a first interview pass resolved. Where a decision has a direct code-side implication (an NVS key, a data structure), that's noted so implementation work has something concrete to anchor to, even though none of it is built yet.

- **World layout**: a single, hand-authored (not procedurally generated) 8×8 grid of 64 discrete, non-scrolling rooms — one LED pixel per room, exactly, matching the LED-matrix pillar with no scaling/compression math needed. The same fixed layout plays out identically every game.
- **World connectivity**: originally "always open" — every room-to-room edge walkable from the start. Relaxed on 2026-09-20 (see "Closed edges" below): some edges are permanently walled so the map has shape, but the rule that matters survives — there are still no *locked* transitions and no per-edge state to persist, and the linear artifact order is still enforced entirely by what a room *contains*, never by making part of the map unreachable. Every room is reachable from the village at all times.
- **Room rendering**: top-down tile view per room (Zelda/Ultima-style overhead perspective), consistent with the player-as-solid-pixel minimap representation.
- **Combat**: real-time, not turn-based — `b` swings/fires the currently-selected weapon with immediate contact-based hits, the same real-time-collision model [Vectortank](vectortank.md)'s opponents already use rather than a separate battle screen.
- **Persistence**: quest progress, inventory, and player position survive a badge power-off via NVS — the same `Preferences`-per-namespace pattern Vectortank's high score already establishes (see its "Kill count and a single anonymous high score" section), rather than Vectortank's own ephemeral per-run state.
- **Artifact count and ordering**: roughly 5-8 artifacts total across weapons/amulets/scrolls, unlocked in a strictly linear order — artifact *N* must be found before artifact *N+1* becomes obtainable/relevant, matching the brief's "collect the artifacts in the right order" framing exactly (not a prerequisite-set or fully-open model).
- **Weapons** (cycled via `x`, swung via `b`): three total, each a straightforward reach/damage/speed tradeoff — **sword** (strongest, implied starting weapon since axe/bow are earned), **axe** (thrown, short range, less damage than the sword), **bow** (arrows, longest range, least damage). Axe and bow are both early-quest pickups rather than starting equipment, so the player begins sword-only and the weapon roster grows as the linear artifact chain progresses.
- **Amulets**: dual-purpose — a passive stat/ability buff while worn (health, speed, resistance, etc., specifics TBD) *and* some amulets double as key items required to progress a story beat (e.g. needed to defeat a boss, open a chest, or trigger an event) — since world connectivity is always-open (no locked room transitions, see above), this gating happens at content the player encounters, not at movement.
- **Scrolls** (read via `y`, the "special action"): primarily narrative delivery — reading one shows story/lore text, not a combat or utility effect. This means `y` is closer to "advance the dry narrative" than a combat verb, a deliberate fit with the brief's "dry series" story tone.
- **Inventory**: small, separate pools per item type rather than one shared list — a handful of weapon slots (only 3 possible weapons exist, so this cap barely matters), a handful of amulet slots, a handful of scroll slots. Exact per-pool capacities are still TBD.
- **World population**: rooms hold a mix of static, fixed-difficulty enemies (no Vectortank-style escalating spawner — a room's enemies are exactly as hard as they were designed to be, every playthrough) and a small number of NPC/shop rooms.
- **Economy**: a simple currency, earned from defeating enemies and/or found loot, spendable at shop rooms for consumables or minor upgrades.
- **Death/failure**: respawn at the last checkpoint (current room's entry point) with health restored and already-collected artifacts kept — no permadeath, no full-world-restart penalty. Exact checkpoint granularity (does a respawned room reset its enemies, or only the player?) is still open.
- **Win condition**: collecting the final artifact in the linear chain unlocks a final boss room; defeating it shows a victory/ending screen — a classic-era "boss at the end" structure rather than a non-combat ritual resolution.
- **Theme**: deliberately generic/vague Norse flavor (runes, longhouses, troll/draugr-style generic enemies) rather than committing to specific named mythology (no Odin/Yggdrasil/etc. references planned) — free to invent as content is authored.

## First playable slice (2026-09-20, `helgrind_game` branch)

The placeholder was replaced by a real `Screen` subclass in `firmware/src/screens/HelgrindScreen.{h,cpp}`, with all static content split into `firmware/src/screens/HelgrindWorld.{h,cpp}`. From here down, this section describes code; the pillars above remain the design brief it implements. It builds clean in the `replay2026` environment but has not yet been played on hardware.

**Core/shell split (2026-09-20).** The game itself — player, enemies, rooms, chain, message box, menus, and all drawing — lives in `firmware/src/screens/HelgrindGame.{h,cpp}` with no firmware dependency beyond u8g2's C API; `HelgrindScreen` is a ~100-line adapter. The seam is four plain-data types: `GameInput` (stick as −1..1 floats plus four edge-triggered button flags), `SaveData` (the nine NVS fields as a struct), a 64-byte minimap brightness array the shell pushes to `badgeMatrix`, and `u8g2_t*` for drawing — obtained on the badge from a new `oled::raw()` accessor (`firmware/src/hardware/oled.h`) so the game draws through the same u8g2 object and fonts the wrapper does, with the wrapper's radius clamp and Liang-Barsky line clip restated in the core. The game never reads `millis()`; every entry point takes `now`. Persistence is a dirty flag (`gameTakeSaveDirty()`) the shell polls after each tick, so the NVS write cadence is unchanged but the game no longer knows `Preferences` exists. The point of the split is the [host harness](#host-harness) below.

**Data shape.** `HelgrindWorld.cpp` holds thirteen 16×6 tile *templates* (meadow, forest, cave, longhouse, shrine, lake, fjord, gate, village, barrow, ruin, bridge, grove — 8px tiles, so a room is exactly 128×48px) and a 64-entry `RoomDef` table giving each room a name, a template, flags, up to three `EnemyKind` slots, an optional 1-based artifact-chain index, an optional NPC, and an optional one-time silver cache. Every template shares the same border with 2-tile doorways centred on all four sides, which is what lets `kRoomFlipX` mirror a template for variety without touching connectivity. `tileAt()` in the screen seals a doorway when it would lead off the world's outer edge or through a closed edge. Room index is `row * 8 + col`, row 0 north — the minimap is literally `badgeMatrix.setPixel(col, row)`, which answers the coordinate-convention question above.

**Closed edges.** `kRoomWallN/S/W/E` in `RoomDef::flags` wall off that side's doorway; `edgeSealed()` checks both the room's own flag and the neighbour's opposing one, so a closure is authored once. The first pass uses them for: Helgrind itself (room 7) approached only from the west along the north row, past Warden's Steps (6, also sealed to the south); a north-west cave complex (rooms 0, 1, 8, 9 — Frost Hollow inside it) with a single mouth at Cold Cave's south door; a two-room mine (4, 12) entered from the south; a bear den (33) with one way in from West Cave; a shoreline along the east column with only a few ways down to the water; and a sheepfold tucked behind a hedge. `firmware/host/helgrind/check-world.py` (`make check` in that directory) parses the world file and fails if any template's four doors aren't mutually connected, any room is unreachable from the village once closures are applied, or an artifact/NPC slot lands on a solid tile; when the host binary is built it also measures every story line with the badge's own font (`helgrind-host --strwidth`) and fails any wider than the message box (117px). It caught two real bugs on its first run — the original lake template's south door was unreachable, and the grove's artifact slot was a tree, which would have hidden the very first artifact.

**Story.** The winter hasn't broken; Helgrind, the gate at the north-east corner of the world, stands open and the dead walk south, and the people sent to look haven't come back. The village believes Hrafn the ferryman drowned the night the mere froze. What actually happened: he rowed the dead north across it, shut the gate behind them and stayed; the cold took him, and what is left of him is what holds the gate open now — he is the "warden" (`kEnemyBoss`, 40 HP) at the end, and killing him is giving him rest. The elder has known all along and told the kinder story. The player learns it in pieces: the fisher heard rowing under the ice, the Ferryman's Scroll ends "do not mourn me", the hermit in the western caves is Hrafn's brother and says the elder knows more than he tells, and the elder admits it when handing over the last scroll — the Gate Scroll (index 6) is not a floor pickup but Hrafn's letter to the elder ("Tell them I drowned"), given in dialogue once the player holds the other six (`kElderGivenArtifact`). The ending closes on the lie standing: the village will tell it as the elder told it. Mechanically the seven artifacts are the things Hrafn left behind, in order; the two mid-chain scrolls are in his hand and each points at the next pickup, and the elder fills the gaps with one line per chain stage (`kElder[8]`, keyed on `nextArtifactIndex()`). Three lore NPCs — skald (village), fisher (the mere), hermit — each have three or four staged lines plus a post-victory line. New Game opens on three intro pages; the first arrival at Helgrind each session shows one page (`gatePage()`: the empty gate, or Hrafn turning); killing him plays three ending pages before the victory menu. All text lives as `Page` structs (title + up to three lines) in `HelgrindWorld.cpp`; the screen's message box is a small queue of Pages advanced with B, so multi-page beats need no special casing.

**Resolved open questions**, as implemented (all of these are cheap to change, they're just the choices the first slice made):

- *Checkpoint granularity*: `enterRoom()` respawns every enemy in a room each time it's entered, including after death — the classic-era rule. Death (`Mode::kGameOver`) offers Respawn, which restores full health at the room's entry point (the doorway tile the player came in through, stored as `entryX/entryY`).
- *Inventory*: there are no slot caps. Held artifacts are a single `uint8_t` bitmask (`Player::arts`, bit *i* = chain index *i*), which is the whole inventory model; separate pools would only matter if items could be dropped or duplicated, and none can.
- *Amulets*: Bear Amulet (chain index 2) is +4 max HP; Frost Amulet (index 5) halves damage taken. Neither gates content — the linear chain (`nextArtifactIndex()`) is the only gate, and the warden simply doesn't spawn in the gate room until all seven are held.
- *Economy*: "silver", awarded per kill from `EnemyDef::silver` (wolf 1, draugr 2, troll 4, Hrafn 20) and from nine one-time caches (`RoomDef::loot`, 2–8 silver each, tracked in a 64-bit `loot` room bitmask in NVS) placed in the rooms the chain doesn't pass through, so wandering pays. Merchant NPCs (Mead Hall at the village, Trader's Hall mid-map) sell one thing: mead, 5 silver for +6 HP, via the Y action.
- *Quest blink*: `questRoom()` blinks the room holding the next uncollected artifact, then the gate room once all seven are held, nothing once won. Since each artifact lives in exactly one room, the setup-vs-payoff ambiguity never arises.
- *Footer*: `HP cur/max`, the 3-letter weapon tag (SWD/AXE/BOW), `$silver`, and `held/7` artifacts.
- *Layout*: village start at room 59 (south edge), Helgrind at room 7 (north-east corner); the chain runs axe (52, Woodsman's Rest) → Ferryman's Scroll (62, Ferry Mere) → Bear Amulet (33, Bear Cave) → Yew Bow (21, Rune Shrine) → Rune Scroll (47, Rune Fjord) → Frost Amulet (9, Frost Hollow) → Gate Scroll (from the elder at 28), pulling the player roughly outward from the village. Difficulty rises with distance: wolves in the south, draugr mid-map, trolls in the northern caves.

**Controls** follow the brief exactly. Stick walks and sets a 4-way facing; A pauses (Resume/New Game/Exit), B attacks, X cycles through unlocked weapons, Y is context-sensitive — merchant/elder when adjacent to an NPC, else reads a rune stone (`kTileRune`) the player is pressed against (`runeStonePage()`: Woodsman's Rest, Wolf Run, Old Cairns, the Rune Shrine and Helgrind's gateposts have their own lines, every other stone shares one), else re-reads the most recently collected scroll. Menus take stick-Y or X to move and B to pick, the same shape as Vectortank's pause overlay. Because Y is the physical UP button, the screen overrides `suppressesForceSleep()` like Vectortank does.

**Combat** is real-time with three weapons in `kWeapons[]`: sword (damage 3, 300ms cooldown, 8px melee box in front of the player), thrown axe (damage 2, 500ms, 63px/s, 29px range — the held axe vanishes while one is in flight and the projectile tumbles through four quarter-turns), bow (damage 1, 350ms, 150px/s, whole room). The player sprite (3-wide head and body, nose and leading arm on the facing side) is only ever drawn facing left or right — `Player::side`, the last sideways facing, so walking up or down doesn't change the pose — with the weapon carried upright one pixel past the arm: sword blade up, axe haft up with the head forward, bow as a 5px arc. A sword swing draws along the *true* 4-way facing to its full 8px reach for its 120ms, so an upward or downward strike shows where it lands. Up/down sprite variants were tried and dropped on device (2026-09-20) as the sideways ones were the only ones that read. Enemies have two behaviours, switched on `EnemyDef::aggroPx` (wolf 36, draugr 44, troll 56, Hrafn 0 = always chasing): outside that radius and unhurt they idle, pausing 0.8–2.8s then hopping one tile in a random clear direction at three-quarter speed, so a room reads as inhabited rather than as a swarm converging on the door; inside it, or once damaged, they chase the player directly. Speeds (wolf 13, draugr 7, troll 5, Hrafn 7 px/s) are a third or less of the player's 40, after two rounds of device play each found them too fast (the original values were 38/22/14/18). Movement uses axis-separated tile collision (`moveWithCollision()`); enemies take knockback on hit and deal contact damage with an 800ms invulnerability flicker on the player. Idle hops draw from a small xorshift seeded from the clock at `gameBegin()`, which keeps host-harness scripts (fixed clock) reproducible.

**Persistence** is the `badge_helgrind` NVS namespace (listed in `firmware/docs/STORAGE-MODEL.md`'s namespace map, which owns that table): `room`, `hp`, `silver`, `arts`, `weapon`, `won`, `loot`, and the entry point `ex`/`ey`. It's written on room change, pickup, purchase, respawn, victory, and screen exit — never per frame. New Game overwrites every key with fresh values rather than clearing the namespace. Resuming always places the player at the saved room's entry point, not their exact last position.

## Host harness

`firmware/host/helgrind/` builds the game core, `HelgrindWorld`, and u8g2's C sources (from the `.pio/libdeps/replay2026/U8g2` checkout PlatformIO already fetched) into one host binary, `helgrind-host`, with a plain GNU `Makefile`. It lives under `firmware/host/` rather than `firmware/test/` on purpose: `test/` is PlatformIO's `test_dir`, and `pio test` would try to compile the SDL driver for the ESP32. The binary has three modes. **Scripted** (`helgrind-host <script> [outdir]`, `make test` runs every `scripts/*.txt`): a text script drives the game against a fixed 16 ms clock — `new`, `load k=v…`, `hold <udlr|none>`, `press <a|b|x|y>`, `wait`, `until <expr> <ms>`, `snap`, `status`, `assert <expr>…`, where expressions are `k=v`/`k>=v`/`k<=v` over the `GameStatus` fields — and writes PNG pairs of both displays; a failed assert fails `make`. **Interactive** (`make play`, needs `libsdl2-dev`, detected via `pkg-config` and optional): an SDL2 window with the OLED at 4×, the minimap as 8×8 warm-white cells, and a help/status panel beneath that is itself a second u8g2 buffer (256×64 in `u8g2_font_6x10_tr`) so no font library is added; arrows are the stick, `Z X C V` are A B X Y, `S` snapshots, `F5` restarts, `Esc` quits, and it runs on the wall clock so movement and attack timing are the badge's. **`--strwidth`**: measures strings in the badge's text font for `check-world.py`, replacing the ad-hoc probe binary the first content pass used.

The code is five small modules with one job each: `png` (a zlib-free greyscale encoder), `display` (the buffer-only SSD1306, page-buffer unpacking, and snapshots — the single place the OLED bitmap is decoded, shared by PNGs and the window), `status` (the observable game fields and the `k=v` matcher used by `assert`/`until`/the panel), `script` (the interpreter), `window` (SDL, compiled to a stub without `HELGRIND_SDL`), and `main`. Because it is the same `gameDraw()` and the same font data, an OLED frame from the harness is the badge's pixels, not a re-implementation. It paid for itself on its first frame: the message box's `B:more` hint was overlapping the third text line, invisible in code and obvious in the PNG (fixed by moving the hint to the title row). What it cannot show: LED colour, key-repeat/debounce (those live in `Inputs`, outside the core), and NVS behaviour. Plain C++17 + C + SDL2 throughout, tested only on Linux (a Pi 5); macOS and WSL/MSYS2 should work but are unverified. The whole of u8g2's clib is compiled, drivers included, because `u8g2_d_setup.c` references every driver — the ~15 MB font table is the slow first build, cached after.

## Remaining open questions

- Whether respawning enemies on every room entry is too punishing once tuned on hardware — the alternative is a per-room "cleared" flag that persists until death.
- Balance: enemy HP, weapon numbers, mead price, and whether the warden (40 HP, 5 contact damage) is beatable with the sword alone. Enemy speed had one device-play pass (2026-09-20); the rest hasn't.
- Sprite legibility at 1-bit: the enemy and tile glyphs are primitive-drawn placeholders and may want XBM bitmaps once the look is settled.
- Room template variety: thirteen templates plus mirroring over 64 rooms still repeats; per-room interior overrides are the next content step if it reads as samey on hardware.
- Whether the closed-edge set is right: the cave complex and mine are dead ends by design, but a player without the minimap habit may find the sealed bear den confusing.
