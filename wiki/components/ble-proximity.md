# BLE Room Presence (disabled in public builds)

`firmware/src/ble/` implements a full BLE room-presence system — `BleBeaconScanner` (venue iBeacon scanning) and `BadgeBeaconAdv` (badge-as-beacon advertising) — but it is not part of the public firmware. `firmware/platformio.ini`'s `[base]` `build_src_filter` excludes the folder outright (`-<ble/>`), and a comment there spells out the reason: "BLE proximity is compiled out for offline firmware. To restore it later, add `-DBADGE_ENABLE_BLE_PROXIMITY` and re-add `+<ble/>`." This is a second, more concrete instance of the [offline-first runtime](../concepts/offline-first-runtime.md) and [public/private scope boundary](../concepts/public-repo-scope-boundary.md) concepts than either page currently documents: the source for a room-tracking feature ships in this public repo, fully implemented, but is switched off at the build level rather than removed, presumably because it depends on venue-side infrastructure (physical BLE beacons) that only makes sense at a live Temporal event. The exclusion is visible from the flashing tooling too, not just the firmware build flags: [Ignition's flash workflow](ignition-flash-workflow.md) has a fully-implemented `verify_badge_ble` activity that watches for BLE scan/advertise log lines, but the per-badge workflow never actually calls it against a public build — it hardcodes a "skipped" result instead, because a badge built from this repo will never emit those log lines in the first place.

## How the scheme works

Venue beacons broadcast a rotating iBeacon proximity UUID, HMAC-derived per 30-second epoch (`epoch30 = unix_time / 30`) — the exact HMAC scheme is shared by both sides via `BleBeaconScanner::computeUuidForEpoch()`, which `BadgeBeaconAdv` calls to build its own outgoing advertisement bytes when the badge advertises itself as a beacon. The iBeacon **major** field carries a room UID that matches the [data bundle](data-bundle.md) pipeline's floor loc-code scheme exactly: `floor_idx * 100 + section_idx * 10`, with off-site locations using the `9xx` prefix documented on that page. `BleBeaconScanner::floorForUid()`/`sectionForUid()` decode a received UID back into the same indices `build-data.py` assigned when it generated `floors.json`, so the map screen can resolve "which section is the badge closest to" without any additional lookup table on-device.

Authentication requires a synced clock: a scanned beacon's UUID is checked against the HMAC computed for the badge's current `epoch30`, so `authFailNoTime()` (NTP never synced) and `authFailMismatch()` (format matched but UUID didn't) are tracked as separate failure counters precisely so a "beacons visible but none authenticate" symptom can be attributed to the right cause.

## Why it can't just run alongside WiFi

Both `BleBeaconScanner` and `BadgeBeaconAdv` are written around a hard resource constraint: the BLE controller (~30 KB) and the WiFi LwIP stack (~50 KB) can't coexist in this build's internal-DRAM budget, so `beginSession()` explicitly shuts down WiFi (deinit + free its DRAM) before bringing BLE up, and `BleBeaconScanner::blocksWiFi()` is a predicate [`WiFiService`](../systems/replay2026-firmware.md) is expected to check before attempting a reconnect while BLE is active or initializing — one more entry in the [internal-DRAM contention](../concepts/internal-dram-contention.md) picture alongside TLS and the MicroPython heap. The BLE controller deliberately stays initialized once brought up rather than being torn down between scans (repeated Arduino BLE deinit/reinit cycles have use-after-free hazards), with `shutdownForExclusiveApp()` as the one exception — a full, permanent-until-reboot BLE shutdown reserved for a hard-takeover app mode that needs every byte of contiguous internal DRAM and will never need BLE again that session, as the now-removed [Doom port](doom.md) once did. A dedicated memory anchor (`reserveMemoryAnchor()`/`releaseMemoryAnchor()`) pre-claims a contiguous internal slab early in `setup()` specifically because MicroPython/LwIP/TLS allocations otherwise fragment the internal heap below the ~32 KB largest-free-block floor that `btdm_controller_init` empirically needs to succeed.
