# Doom Port

The badge runs a DoomGeneric-based Doom port as an "app mode" gated behind `-DBADGE_HAS_DOOM`, using the shareware `doom1.wad` loaded from FATFS at `/doom1.wad` (see [licensing boundaries](../concepts/third-party-licensing.md) — the WAD and the vendored DoomGeneric engine sit outside this repo's MIT license). `firmware/src/doom/README.md` is the authoritative architecture reference; `firmware/codeDocs/DOOM.md` is an earlier design sketch that predates the implementation and should not be trusted over the current source or the `src/doom/README.md` file it explicitly defers to.

## Resource ownership during Doom mode

Doom mode is a hard takeover, not a cooperating app: `DoomScreen::launchDoom` deactivates the GUI, then `doom_resources_enter()` claims the badge — forcing 240 MHz performance mode with no light sleep, disconnecting/disabling WiFi, stopping IR hardware (Doom's sound module reuses the IR TX pin, GPIO 2, as an I2S clock line), suspending the normal input-interrupt path so the Doom task reads GPIO/ADC directly, and pausing the GUI/OLED, background haptics, LED, IMU, sleep, battery, and config services. `doom_app_enter()` then spawns the actual game task pinned to Core 1 with a 32 KB stack; Core 0's main loop skips its normal polling and only watches for `doom_app_stop_requested()`. Exiting reverses every one of those steps in `doom_resources_exit()`, including restoring [LEDAppRuntime](led-app-runtime.md)'s ambient ownership — Doom is a second, mutually-exclusive claimant on the same LED matrix and OLED that the ambient runtime and MicroPython apps otherwise share.

## Rendering pipeline

The engine renders at 160x100 (`DOOMGENERIC_RESX`/`RESY`, which must live in `platformio.ini` `build_flags` rather than `library.json` because DoomGeneric's sources are pulled in via `build_src_filter`, not PlatformIO's Library Dependency Finder). `doom_render.cpp` box-filter downsamples that to 128x64 luma, runs it through a gamma LUT, and either applies a fixed threshold or Bayer 2x2/4x4 ordered dithering to pack it into the same 1bpp SSD1306 page format the [badge's OLED](badge-device.md) uses elsewhere, with a proportional auto-gamma controller that converges the threshold toward a target white-pixel percentage (50% for gameplay, separately tunable for splash screens) rather than using a fixed cutoff. Big buffers — the 64 KB screen buffer, ~200 KB of zone memory, and the engine's view/plane/segment tables — are allocated from PSRAM via `doom_esp32_mem.c`.

## Input and the LED matrix HUD

Input bypasses the normal badge input service: `doom_input.cpp` reads GPIOs/ADC directly since interrupts are suspended for the duration. The two control surfaces stay distinct: the analog joystick drives turn and forward/back movement, while the four discrete d-pad buttons handle everything else — UP fires, DOWN opens doors, and LEFT+RIGHT strafe when tapped individually (`joy_x`'s own left/right also strafes, read separately from the buttons). Holding the LEFT and RIGHT *buttons* together for 1.5 seconds (`kExitComboMs`) is the universal exit combo — a combination only possible because they're two independent digital buttons, not two positions of the single analog stick, which can only report one X value at a time. UP+DOWN held together maps to `KEY_ESCAPE` (menu/pause) using the same simultaneous-button-press pattern. `doom_hud_matrix.cpp` moves the HUD off the OLED entirely onto the [8x8 LED matrix](badge-device.md): four pages (health/armor/ammo/keys) cycle every 1.1 seconds, any state change temporarily jumps to the relevant page, and low health pulses the health page's corners — the same matrix hardware [LEDAppRuntime](led-app-runtime.md) owns outside of Doom mode, reused here under Doom's own resource claim instead.

## Sound

`doom_sound.cpp` repurposes the vibration motor's GPIO as a 1-bit I2S PDM speaker (`DG_sound_module`; music is a no-op stub), which means haptic pulses and Doom's audio are mutually exclusive at the hardware level — both drive the same motor pin through different peripherals (I2S PDM vs. the MCPWM channel haptics normally use), so sound has to tear down and rebuild that peripheral claim on entry/exit. WAD sound lumps (`DS*`) carry an 8-byte header (format tag, sample rate, sample count) ahead of raw 8-bit PCM, which `StartSound` resolves via `W_CacheLumpNum` and rescales into the I2S DMA buffer by the user-tunable `sound_volume`/`sound_pdm_duty` settings.
