# NEC IR Protocol Layer

`firmware/src/hw/ir/` is the lowest layer of the badge's IR stack — pure RMT-hardware and bit-encoding code with no dependency on anything above it, which is exactly why `firmware/src/README.md` keeps it in its own folder separate from `ir/BadgeIR.{cpp,h}` (the transport `irTask` wraps this in) and `boops/` (the protocol on top of that transport — see [Boops](badge-boops.md)). Three distinct codecs share the same RMT TX/RX driver pair (`nec_tx.c`/`nec_rx.c`):

- **`nec_mw_encoder`/`nec_mw_decoder`** — the badge's own multi-word-plus-CRC32 dialect, the one actually used by Boops. A frame is `[NEC leader] [word0]...[wordN-1] [CRC32] [end pulse]`, up to `NEC_MAX_WORDS = 64` words.
- **`nec_consumer`** — a separate, single-word "Flipper-style" consumer NEC codec (canonical `addr`/`~addr`/`cmd`/`~cmd` layout, ~30%-tolerance edge timing to cope with cheap real-world remotes) used by IR Playground sub-apps to record and replay ordinary TV/audio remotes. This codec deliberately never touches RMT hardware directly — it only produces/consumes `rmt_symbol_word_t` arrays that `BadgeIR` feeds through the same channel and a copy encoder, so consumer-remote capture and the badge's own multi-word dialect can share one physical transport without either codec needing to know about the other.
- **`nec_rx`'s raw-symbol callback** — an optional hook invoked on every received burst *before* the multi-word decoder runs, specifically so MicroPython (or `nec_consumer`) can inspect a frame that doesn't parse as the badge's own dialect, without losing back-compat for frames that do.

## Two sizing regressions, both root-caused in comments

Two constants in this layer were each shrunk once for an unrelated reason and each silently broke Boops before being reverted — both call out the regression directly in a code comment, which is unusually good self-documentation of past incidents:

- **`NEC_MAX_WORDS`** (`nec_mw_encoder.h`) was briefly tightened from 64 to 8 back when WiFi still handled post-boop sync, so a smaller IR payload ceiling seemed safe. Once WiFi was removed and [Boops](badge-boops.md) became the *only* way peers exchange name/title/company/bio, that 8-word ceiling silently dropped any `DATA` frame whose payload exceeded ~20 bytes (`encodeDataFrame` returns 0, and the caller quietly skips sending it) — the peer would then retransmit `STREAM_REQ` forever waiting for data that was never coming. It was restored to 64 to match the original "boops actually work" commit (`75db63a8`), sized to fit a worst-case 32-byte bio chunk plus headers.
- **`NEC_RX_SYMBOL_COUNT`** (`nec_rx.h`) was briefly shrunk to 320 — enough for 8-word frames only — which silently truncated any `DATA` frame carrying more than one TLV once the exchange protocol started batching multiple `(tag, chunkIdx, len, bytes)` groups per frame. It's back to 2112 (`1 leader + 32*(64+1 CRC) + 1 end`, rounded up to the 64-symbol multiple ESP32-S3's RMT DMA requires) and the header comment explicitly ties this constant to `NEC_MAX_WORDS`, flagging that the two must be changed together.

Both bugs share a shape worth generalizing from: a payload-size ceiling was tightened for a reason that made sense at the time (WiFi handling large transfers; a smaller expected frame size), and both silently degraded — no crash, no error, just data quietly not arriving — until the surrounding protocol changed underneath the assumption. Any future change to `NEC_MAX_WORDS` or `NEC_RX_SYMBOL_COUNT` should double-check both the TX and RX sides move together, and check the [Boops exchange phase](badge-boops.md)'s current `kMaxTlvBytes = 120` assumption still fits.

## Transmit and receive lifecycle

`nec_tx` uses FreeRTOS task notifications for completion signaling, which imposes a real constraint: `nec_tx_init`, `nec_tx_send`/`nec_tx_send_nowait`, and `nec_tx_wait` must all run from the same FreeRTOS task for a given context, since the context stores exactly one task handle to notify. A two-slot ring buffer (`NEC_TX_RING_DEPTH = 2`, deliberately one more than the RMT driver's own `trans_queue_depth = 1`) exists because each in-flight RMT transaction needs its own live payload buffer — the RMT encoder reads asynchronously from it after `rmt_transmit()` returns, so the caller can't safely reuse or free that memory until the transaction completes. `nec_tx_send_nowait` is what lets [Boops' streaming exchange](badge-boops.md) queue back-to-back `DATA` frames without blocking on each one's completion. The carrier frequency (38 kHz default) and duty cycle are runtime-adjustable — `nec_tx_set_carrier_duty` exists specifically so a self-loopback test can lower LED drive current without overwhelming even a covered sensor, and `nec_tx_set_carrier_freq` widens the range to 30-60 kHz for captured consumer remotes (Sony/RC5/RC6) that don't use 38 kHz.
