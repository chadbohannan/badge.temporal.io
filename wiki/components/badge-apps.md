# Badge App Authoring Model

MicroPython apps live under `firmware/initial_filesystem/apps/` as either a single `.py` file or a folder with a `main.py` entry point, and run top-to-bottom when launched, calling `exit()` to return cleanly to the menu. All `badge.*` API functions are auto-imported into an entry script's global scope, so a one-file app can call `oled_println(...)` directly with no `import badge` — folder-app internal modules don't get that auto-import and need `from badge import *` explicitly. This authoring surface sits on top of the native bindings described on the [MicroPython bridge](micropython-bridge.md) page; this page covers the app-author-facing conventions and helper libraries instead of the C++ binding plumbing.

## Shared helper libraries

Two libraries under `firmware/initial_filesystem/lib/` keep apps visually and structurally consistent instead of every app reinventing chrome and lifecycle handling:

- `badge_ui.py` wraps the native UI chrome (`ui_header`, `ui_action_bar`, glyph-based button hints) so Python screens match the built-in firmware menus pixel-for-pixel, falling back to a pure-Python implementation when the native helper isn't present.
- `badge_app.py` supplies `run_app(name, callback, cleanup)` (writes uncaught exceptions to `/last_mpy_error.txt` and shows a badge-native crash screen instead of a blank display), `with_led_override(callback)` (pairs `led_override_begin()`/`led_override_end()` around a call so foreground LED drawing always restores [LEDAppRuntime](led-app-runtime.md)'s ambient pattern on exit, even on an exception), `ButtonLatch` (edge-triggered button state), `GCTicker` (paces `gc.collect()` on a timer for long-running loops against the [2 MB PSRAM Python heap](badge-device.md)), and `DualScreenSession` (frame-timing helper for apps that drive the OLED and LED matrix at independent rates).

Users can also force-exit any running app by holding all four face buttons for about a second — the escape chord raises `SystemExit` and returns to the menu without the app needing to handle it.

## How JumperIDE apps reach the menu without a reboot

`firmware/src/apps/AppRegistry.{h,cpp}` is what lets JumperIDE push a script to `/apps/<slug>/main.py` and have it appear in the menu immediately via `badge.rescan_apps()`, instead of requiring the four hand-wired main-menu edits described above. The registry deliberately never imports or executes the Python module to discover it — it does a fast text scan of the first ~2 KB of `main.py` for `__title__`/`__icon__`/`__description__` dunders with hand-rolled parsing, specifically so boot and rescan stay fast even with the full `kMaxDynamicApps = 32` slots occupied. If `__icon__` names a `.py` file, the registry scans that file's `DATA = (...)` tuple for a 12x12 packed-XBM icon (24 bytes) rather than executing it either; a missing or unparsable icon falls back to a generic apps icon so the entry still shows up. A `__matrix_title__`/`matrix.py` pair on a folder app is what makes `AppRegistry` set `hasMatrixApp`, which is how `LEDScreen`'s carousel learns to offer that app's ambient pattern as a [`PythonApp` LED mode](led-app-runtime.md) alongside the native ones.

A separate small store, `firmware/src/apps/MenuOrderStore.{h,cpp}`, persists user-customized menu ordering in NVS (namespace `menu_order`) keyed by an FNV-1a hash of each menu label rather than the label text itself, since raw labels can exceed the 15-character NVS key limit — collisions are accepted as extremely unlikely for the small label set the menu carries, with "last writer wins" as the deliberately simple resolution since a user can always reorder again.

## Getting a production app into the main menu

Normal firmware only exposes attendee-facing apps in the main grid menu; the generic Apps menu (which lists every loose `.py` file for development) is dev-build-only. Shipping an app to the real menu takes four coordinated edits: the app folder under `initial_filesystem/apps/<app>/main.py`, an `icon.py` plus a bitmap added to `firmware/src/ui/AppIcons.h` if it uses the LED matrix, a launcher action in `firmware/src/ui/GUI.cpp` calling `mpy_gui_exec_file("/apps/<app>/main.py")`, and a `GridMenuItem` entry in `kBadgeMenuItems`. One-off diagnostics and API demos (see `firmware/initial_filesystem/apps/diagnostics/`, e.g. `api_test.py`, `input_test.py`, `ir_loopback_test.py`) stay in the dev-only Apps menu rather than getting a main-menu launcher.

## The dev force-refresh loop

App files normally ship inside `fatfs.bin`, and re-flashing a ~6-7 MB FATFS partition (see the [badge device](badge-device.md) storage table) on every edit is too slow for iteration. `-DBADGE_DEV_FORCE_REFRESH="/apps/my_app/,/lib/badge_ui.py"'` in `platformio.ini`'s `build_flags_common` (note the required outer single-quotes, matching the existing `'-DFFCONF_H="ffconf.h"'` convention — without them the embedded double quotes break SCons and the macro expands to bare tokens) does two things automatically: `generate_startup_files.py` bakes the listed paths into `StartupFilesData.h` as extra app0 content, and `provisionStartupFiles()` overwrites the on-FATFS copy of every matching file at boot, even overwriting a JumperIDE-side edit. The net effect is that `pio run -e replay2026 -t upload` alone (firmware-only, no `uploadfs`) is enough to push new app code during iteration — but the flag must be removed before a production build, since leaving it set bloats app0 and silently discards any user JumperIDE edits to those files on every boot. A companion runtime-only mechanism, dropping a `/dev_force_refresh.txt` marker file (same comma-separated syntax, one-shot, auto-deleted after the next boot) directly onto FATFS, achieves the same per-file refresh without a firmware rebuild, but only for files already covered by `lib/`/`matrixApps/` or a prior build's bake flag.

## Validating an app change

`black` (formatting) and `python3 -m py_compile` (syntax) are host-side checks that don't replace an on-device smoke test for input, timing, display ownership, LED override, or MicroPython heap behavior. `python3 scripts/generate_startup_files.py` must be re-run (or triggered by a normal `pio run`) after any app-file edit, and both `src/micropython/StartupFilesData.h` and `scripts/startup_hash_history.json` are committed alongside the source change — `StartupFilesData.h` is generated and must never be hand-edited.

## A note on stale environment names in app-facing docs

Several app-authoring docs — `firmware/initial_filesystem/apps/README.md`, `firmware/initial_filesystem/docs/API_REFERENCE.md` and `MicroPythonDeveloperGuide.md`, `firmware/micropython/README.md` and its `usermods/temporalbadge/README.md`, and both files under `docs/markdown/` — give build/flash examples using `pio run -e echo` or `echo-dev`. None of those environments exist in the current public `firmware/platformio.ini`, which only defines `replay2026` and `replay2026-expanded` (see the [firmware system page](../systems/replay2026-firmware.md)). This looks like exactly the leftover "old prototype target name" `AGENTS.md` warns contributors to avoid exposing (see the [public/private scope boundary](../concepts/public-repo-scope-boundary.md)) — copy-pasting those commands from the docs as written will fail with an unknown-environment error; substitute `replay2026` (or a locally-added dev environment) until those docs are corrected.
