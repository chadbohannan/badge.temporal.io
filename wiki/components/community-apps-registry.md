# Community Apps Registry

Community Apps is the mechanism for third-party MicroPython apps to reach badges without being baked into the factory filesystem. Contributors add one folder per app under `community_apps/` at the repo root — `main.py` (entry point), `community.json` (registry metadata: at minimum `name`, `description`, `contributors`), and a `README.md` — using a lowercase, underscore-separated slug, because the badge installs the folder directly to `/apps/<app>/` on that exact name.

## Why this is a separate path from the default filesystem

Everything under `firmware/initial_filesystem/` ships to every badge via the factory image or `uploadfs`, as covered on the [storage model](storage-model.md) page. Community Apps deliberately don't: they're published as a generated `community_apps.json` GitHub Release asset (built by `firmware/scripts/generate_startup_files.py` from the `community_apps/` folder contents, and regenerated by the [release workflow](release-workflow.md) before every firmware build) and installed on-demand from the badge's Community Apps screen over WiFi. That keeps the factory image size bounded and lets new apps ship between firmware releases without needing a full reflash — a badge that never runs the installer for a given app never carries its code.

An app's registry entry also determines what shows up in the on-badge Apps menu: `main.py` should declare `__title__`, `__description__`, and `__icon__` near the top so the installed app displays correctly, distinct from `community.json`'s registry-level metadata used by the Community Apps screen itself before install.

The actual on-badge download mechanism isn't Community-Apps-specific: it's the generic `AssetRegistry` fetcher covered on the [OTA and assets](ota-and-assets.md) page, which also delivers `doom1.wad` and other non-app assets through the same `registry.json` schema and the same `community_apps_url` setting.

## Review and validation

Local pre-submission checks mirror what CI does: `python3 firmware/scripts/generate_startup_files.py` regenerates the registry, `python3 -m json.tool firmware/build/community_apps.json` validates the JSON shape, and `python3 -m py_compile community_apps/<app>/*.py` catches syntax errors before a PR is opened. The `evaluate-community-app.yml` GitHub Actions workflow runs an automated submission review on Community App pull requests checking folder shape, metadata completeness, common MicroPython risk patterns, docs impact, licensing, and whether the change needs a matching docs update.

Generated registry output (`community_apps.json` itself) is never committed — only app source, metadata, docs, and license notices are. The registry is rebuilt by the [release workflow](release-workflow.md) at release time, which is the only place the authoritative, published `community_apps.json` comes from.

## What's actually in `community_apps/` today

Three apps: Tardigotchi (aask42), Durable Snake, and Starfield Nametag (both by Alexandre Roman, imported from his separate `temporal-replay-2026-badge-apps` repository). Durable Snake and Starfield Nametag both follow the multi-file folder convention (`main.py` plus an `_engine.py` module) and both lean on the shared [app authoring helpers](badge-apps.md) — `DualScreenSession`, `with_led_override`, `badge_ui` — rather than reimplementing chrome and LED-override bookkeeping, which is the same pattern factory-shipped apps under `firmware/initial_filesystem/apps/` use. Their imported origin also means they carry Apache License 2.0 terms rather than this repo's MIT default; see the [third-party licensing](../concepts/third-party-licensing.md) page for the full boundary between what's MIT, GPL, and Apache in this codebase.
