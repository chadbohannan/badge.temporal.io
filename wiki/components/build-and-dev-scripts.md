# Build and Developer Scripts

`firmware/scripts/` holds a dozen-plus Python files, but only four are actually wired into the build: `platformio.ini`'s `[base]` `extra_scripts` runs `inject_version.py`, `generate_build_wifi_config.py`, and `generate_startup_files.py` as `pre:` steps on every environment, and `[env:replay2026]` adds `normalize_bundle_symbols.py` (`post:`) on top of that. (A fifth, `upload_doom_wad.py`, was removed 2026-09-17 along with the rest of the [Doom port](doom.md) — see below.) The rest — `build_recovery_image.py`, `fetch_micropython_sources.py`, `render_button_glyphs_svg.py`, `upload_dual.py`, `verify_firmware_version.py`, and `ir_block_battle_serial.py` — are standalone tools invoked by hand or from CI, not PlatformIO hooks. `badge_sync.py` and `capture_oled_fb.py` are covered on their own pages ([badge_sync](badge-sync.md), [capturing OLED screenshots](../runbooks/capturing-oled-screenshots.md)).

## The automatic pre-build chain

Three `pre:` scripts run in sequence before every `pio run`, in the order `platformio.ini` lists them:

1. **`inject_version.py`** reads `firmware/VERSION` (the same file [the release workflow](release-workflow.md) watches) and injects it as two build flags with different names — `FIRMWARE_VERSION` for `BadgeVersion.h` and `BADGE_FIRMWARE_VERSION` for the MicroPython port's `mpconfigport.h` REPL banner — because the two headers were already wired to different macro names before this script existed, and unifying them would ripple into `BootSplash`, `DiagnosticsScreen`, and `MICROPY_BANNER_MACHINE`. Both headers keep `#ifndef` fallbacks so a bare `pio run` (or an Arduino IDE build) without this script still compiles, just reporting a hardcoded fallback string instead of the real version.
2. **`generate_build_wifi_config.py`** writes `src/infra/BuildWifiConfig.generated.h` from `BADGE_WIFI_SSID`/`BADGE_WIFI_PASS` (env vars or a gitignored `firmware/wifi.local.env`). Credentials are stored XOR-obfuscated with a SHA-256-derived per-build keystream — its own docstring is explicit that this "keeps secrets out of settings.txt, NVS, and casual `strings` output" but "is not cryptographic protection against a motivated firmware reverse engineer." Both SSID and password must be set together or neither; the password is validated to 8-64 bytes (WPA2's own range) before the header is written.
3. **`generate_startup_files.py`** — the survival-floor / manifest / Community Apps registry generator already covered in detail on [badge apps](badge-apps.md) and [the storage model](storage-model.md).

`[env:replay2026]` layers one more script on top of the shared `[base]` chain:

- **`normalize_bundle_symbols.py`** (`post:`) fixes a portability bug in how PlatformIO's `board_build.embed_files` embeds [`data/out/bundle.bin`](data-bundle.md): `objcopy` mangles the *absolute path* of the embedded file into the linker symbol name (e.g. `_binary__home_alex_..._bundle_bin_start`), so the resulting `.o` only links on the machine that built it. This script runs `objcopy --redefine-sym` right after the `.txt.o` is produced, renaming whatever long symbol objcopy actually emitted (discovered via `nm`, not reconstructed from the path) back to the short, path-independent form `DataCache.cpp`'s `asm("_binary_bundle_bin_start")` expects. It's idempotent — re-running against an already-renamed object is a no-op — which matters because PlatformIO's incremental builds can re-invoke post-actions on unchanged objects.

## Standalone tools (not wired into any build)

- **`build_recovery_image.py`** assembles a flat, single-file 16 MB image (bootloader + partition table + `boot_app0.bin` + `firmware.bin` + `fatfs.bin`, merged with `esptool merge_bin --fill-flash-size 16MB`) that end users can flash with one `esptool.py write_flash 0x0 ...` command, no source checkout required. Its own docstring notes the public release workflow currently builds the equivalent factory artifact with `make_factory.sh replay2026` instead — this script is a documented, functionally-overlapping alternative path, not the one CI actually uses.
- **`fetch_micropython_sources.py`** vendors upstream MicroPython files (from a pinned tag, `v1.27.0` by default) that the embed tarball doesn't ship — `network.WLAN`, `socket`, `ssl`, `_thread`, `espnow`, `bluetooth` support — into `lib/micropython_embed/src/`, gated behind opt-in build flags (`REPLAY_ENABLE_FULL_NETWORK`, `REPLAY_ENABLE_BLUETOOTH`, `REPLAY_ENABLE_ESPNOW`, `REPLAY_ENABLE_THREAD`) that the public `replay2026` environment doesn't set. It's invoked once per checkout from `ignition/setup.sh` and is safe to re-run since it only writes files whose content actually changed.
- **`verify_firmware_version.py`** is a CI-only guard: it fails if a built `firmware.bin` doesn't contain the exact version string from `firmware/VERSION` as a byte substring, catching the case where a release asset would silently report the wrong version after OTA. This is the check [the release workflow](release-workflow.md) runs before publishing artifacts.
- **`render_button_glyphs_svg.py`** re-renders the byte arrays from `firmware/src/ui/ButtonGlyphs.cpp` (see [UI conventions](ui-conventions.md)) as scalable SVGs — but its default output directory is `../../Jumperless-docs/docs/img/badge-buttons/`, a sibling checkout outside this repo entirely. This script exists in `badge.temporal.io` to generate documentation assets for JumperIDE's own docs site, not for `docs/` in this repo.
- **`ir_block_battle_serial.py`** drives the IR Block Battle community app over two badges' USB serial ports simultaneously (auto-detecting up to two `/dev/cu.usbmodem*`/`ttyACM*` ports, labeling them A/B) for manual smoke-testing — it types single-character game commands (movement, rotation, Tetris-line sends) from a `--a`/`--b` token sequence and logs both badges' serial output with timestamps side by side. It isn't part of any automated test suite; it's a manual two-badge test harness.
- **`upload_dual.py`** overrides PlatformIO's `UPLOADCMD` to flash every detected `/dev/cu.usbmodem*`/`ttyACM*` port concurrently via direct `esptool` calls in parallel threads. It is **not currently referenced anywhere in `platformio.ini`**, so `pio run -t upload` does not use it by default — it would have to be added to an environment's `extra_scripts` to take effect. Functionally it duplicates what [Ignition's `FlashBadgesWorkflow`](ignition-flash-workflow.md) already does properly (per-badge Temporal child workflows with retry, verification, and progress reporting), which is the more likely reason it was never wired in rather than an oversight.

Standalone tools are found in the [known cruft ledger](../syntheses/known-cruft-and-dead-code.md) where they represent something more than "just an optional script" — see `upload_dual.py`'s entry there.
