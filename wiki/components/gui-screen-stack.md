# The Screen Stack

`firmware/src/screens/Screen.h` defines the badge's entire GUI as a stack of `Screen` objects, managed by `GUIManager` (`firmware/src/ui/GUI.{h,cpp}`), an `IService` on the [cooperative scheduler](scheduler.md). Every screen implements `render()` and `handleInput()`; `onEnter`/`onExit`/`onResume` distinguish a fresh push from returning to a screen because the one above it popped, and `needsRender()` defaults to true but can be overridden to skip repainting when nothing changed (the QR pairing/update screens do this because re-encoding a QR bitmap every frame is expensive). Rendering and input handling within a screen lean on the shared conventions covered on the [UI rendering conventions](ui-conventions.md) page rather than each screen reinventing text layout or button-hint copy. `GUIManager::kMaxScreens = 40` and `kMaxStack = 6` are both hard caps — the max-screens constant carries a comment noting it was bumped up from 16 after the registration table actually hit that old limit and started silently dropping screens past it (`registerScreen` has no way to report a full table other than dropping the excess), which is why new screens should be checked against headroom rather than assumed to always register successfully.

## Three base classes cover almost every screen

Rather than every screen implementing rendering and input from scratch, three base classes absorb the repeated cases: `ListMenuScreen` (scrollable single-column lists — settings, haptics test menu, most sub-navigation), `ModalScreen` (full-screen or inset popups with shared chrome, fade transitions, and swap-aware action-chip footers — the map's section-detail popup and the schedule event-detail popup both subclass this rather than reimplementing push/pop chrome), and `GridMenuScreen` (the icon-grid main menu and Apps/Games submenus, driven by a `GridMenuItem[]` array with a `visible` predicate function pointer, an optional `badgeFn` for the small numeric badge some tiles show, and an `order` sort key). That `order` field is exactly what [`MenuOrderStore`](badge-apps.md) and `AppRegistry`'s `__order__` dunder parsing feed into: the main menu is rebuilt by combining a curated base array position, any dynamic app's requested order, and a user's NVS override, then `std::stable_sort`-ing so ties fall back to array order.

`GridMenuScreen::drawHeader()` swaps the header's title for the wearer's first name whenever `badgeIsActivated(badgeState)` is true (paired or offline both count, so a temporary WiFi drop-out doesn't bounce the header back to the generic "MENU" title) — `firstNameFromBadgeName()` extracts it and `OLEDLayout::drawStatusHeader()` draws it exactly like any other screen's title. It used to read "Hi <first>"; the "Hi " prefix was dropped so the header reads as a plain first-name label, matching the terser one-word titles other screens use in the same slot.

A fourth shape exists outside those three: a screen with a real-time render loop that implements `render()`/`handleInput()` directly with no shared base class, because there's no list/modal/grid structure to inherit. [`VectortankScreen`](vectortank.md) is the concrete example — camera movement, projectile physics, and particle simulation all live in its own `render()`/`handleInput()`, not in any shared chrome.

`ContactsScreen` and `AssetLibraryScreen` are both concrete `ListMenuScreen`s that show the pattern's range: `ContactsScreen` walks `/boops.json` once per `onEnter`/`onResume` into a PSRAM-backed `BadgeBoops::PeerEntry` array (via `BadgeMemory::allocPreferPsram`, since the max contact count would be wasteful to reserve in internal DRAM permanently — see [internal-DRAM contention](../concepts/internal-dram-contention.md)), while `AssetLibraryScreen` synthesizes an extra row 0 ("Download all" / "All up to date") ahead of the real [AssetRegistry](ota-and-assets.md) entries and kicks a Core-0 background refresh whose completion it polls from `onUpdate()` rather than blocking the GUI tick on the network round trip. `MenuOrderScreen` is a `GridMenuScreen` variant used specifically for the "Reorder Menu" screen: an X-press "picks up" the row under the cursor, and subsequent joystick moves swap it down the list live rather than just moving the cursor, before `commitAndExit()` writes each row's new index (spaced by 10, so future curated-tile inserts can land between existing user picks without renumbering everything) into [`MenuOrderStore`](badge-apps.md). The [Schedule Screen](schedule-screen.md) and its pushed `ScheduleDetailModalScreen` are a fourth example, showing the `ModalScreen` base class's own range: a paginated, two-column event list with a selection frame that grows across multiple rows for a long event.

## The nametag overlay is IMU-driven, not screen-driven

`GUIManager::setNametagMode(bool inverted)` is called from the main loop's IMU flip handler, not from any individual screen, and runs its own small state machine (`kDisabled`/`kShown`/`kHidden`/`kPendingEnter`) layered on top of whatever screen is currently active: flipping the badge upside down shows a full-screen nametag after a short guard delay, any face-button press dismisses it and starts a 30-second idle timer, and it silently reappears if that timer elapses with no further input. A handful of screens (the Boop screen is the one called out in the header) suppress the nametag overlay while still applying the flip's *input* orientation change — the two are deliberately decoupled so a screen that's actively mid-interaction (like an IR exchange) doesn't get visually interrupted by the nametag just because the wearer moved.

## A gate that no longer gates anything

`Screen::access()` defaults to `ScreenAccess::kPairedOnly`, and the enum also has `kAny` and `kUnpairedOnly` — reading like a leftover pairing-flow access-control system from before the [offline-first](../concepts/offline-first-runtime.md) redesign removed pairing entirely. It's not dead source excluded from the build the way [BLE](ble-proximity.md) is: `GUIManager::screenAllowedForBadgeState()` is live, compiled, and called on every screen transition — it just always returns `true` for both `kAny` and `kPairedOnly` (i.e., for every screen that actually exists in the tree, since nothing currently declares `kUnpairedOnly`), and `homeScreenForBadgeState()` unconditionally returns `kScreenMainMenu` regardless of any badge state. `UpdateFirmwareScreen` still explicitly overrides `access()` to `kAny`, which reads as meaningful but currently makes no observable difference from the default. This is a third concrete instance of the [public/private scope boundary](../concepts/public-repo-scope-boundary.md) pattern — alongside excluded BLE source and stale `-e echo` docs — where an internal/prior badge generation's concept (paired vs. unpaired access) survives as live, working, but functionally inert code rather than being deleted.

## A second, mostly-dead render path underneath `GUIManager`

`firmware/src/ui/BadgeDisplay.cpp` predates `GUIManager` and still owns the OLED for one narrow boot-time window: `main.cpp`'s `setup()` sets `badgeDisplayActive = true` right after the boot splash, and `oled::update()` (`firmware/src/hardware/oled.cpp`) checks that flag before doing anything else — while it's true, every OLED refresh goes through `BadgeDisplay.cpp`'s free-function `renderScreen()` instead of the screen stack. `renderScreen()` switches on a global `RenderMode` enum (`MODE_BOOT`, `MODE_QR`, `MODE_BOOP`, `MODE_MENU`, `MODE_INPUT_TEST`, `MODE_BOOP_RESULT`, `MODE_INFO`), but across the whole boot sequence `renderMode` is only ever assigned `MODE_BOOT` (its initializer) and then, once, `MODE_MENU` — the same statement (`main.cpp:380`) that flips `badgeDisplayActive` back to `false` and comments "Boot/pairing rendering is complete. From here, GUIManager owns OLED rendering." Nothing in the tree ever sets `renderMode` to `MODE_QR`, `MODE_BOOP`, `MODE_INPUT_TEST`, `MODE_BOOP_RESULT`, or `MODE_INFO` while `badgeDisplayActive` is true, and `renderScreen()`'s `switch` has no `case` for any of them anyway — they fall through to `default: break`. That leaves `renderQR()`, `renderBoop()`, `renderInputTest()`, and `renderBoopResult()` — four fully-implemented static functions in `BadgeDisplay.cpp` that reference live state (`BadgeBoops::boopStatus`, `Inputs::joyX/joyY`, `IMU::isFaceDown()`) — structurally unreachable. They read as a pre-`GUIManager` design where the whole badge, not just boot/pairing, ran through this one `RenderMode` switch; `GUIManager` grew its own equivalents instead of replacing these (its `renderNametagOverlay()` is a distinct, separately-maintained implementation from this file's own `renderNametag()`, which — inside the still-live boot window — is one of only two branches actually reachable, gated on `TILT_SHOWS_BADGE` and a nonempty `badgeName`). See the [known cruft ledger](../syntheses/known-cruft-and-dead-code.md) for the summary entry.
