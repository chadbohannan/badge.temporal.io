# PACKIT: Tetris-Inspired Block-Packing Game

PACKIT is the working title for a new native badge game, kicked off on the `packit_game` branch (created 2026-09-20 off `main`@`732a69b`, the commit that landed [Helgrind](helgrind.md)). Unlike Helgrind and [Vectortank](vectortank.md), which each filled an existing "coming soon" menu tile, PACKIT has no placeholder to inherit — both the `kScreenHelgrind` and `kScreenVectortank` tiles are now spoken for (`firmware/src/screens/Screen.h`), so shipping this means adding a genuinely new entry to the main menu. This page is a live design doc: the brief and interview sections below record the design as agreed, and "First implementation slice" records what's actually built and tested so far — a firmware-free game-state core, no rendering or menu wiring yet.

## Radical redesign: face-view 2D board, not a top-down 3D shaft (2026-09-21)

After several rounds of tuning (perspective math, wireframe fidelity, well depth, piece-set size — all documented below), the top-down true-3D shaft was judged **unplayable at 128×64**: even with every legibility fix applied, there simply isn't enough screen resolution for a real 3D projection to read clearly. Rather than keep tuning a concept that's fighting the hardware, the design pivots to a standard face-on Tetris view — the well becomes a flat 2D grid viewed straight-on, like classic Tetris, while individual blocks keep a pseudo-3D "chunky cube" look purely as a rendering style, not as gameplay geometry. This section is the brief as given; it supersedes the "Confirmed design decisions" and "First implementation slice" sections below wherever they conflict, which those sections still describe in full for history (per the wiki's rule against silently overwriting prior decisions).

**The brief, verbatim intent:**

- Abandon the top-down camera and the depth (`z`) axis entirely — no more shaft, no more "descends away from camera." The board is a single flat plane of blocks, viewed face-on, exactly like standard Tetris.
- Blocks keep a 3D *look* (the cube styling built for the shaft version) even though the well itself is now 2D.
- The falling piece is **no longer transparent/wireframe** — it draws the same way settled blocks do. (This retires the "transparent falling piece vs. opaque settled piece" distinction the shaft version was built around.)
- The screen is wide (128×64, landscape), so the board should be **wider than it is tall** — the opposite proportion from a classic Tetris well (10×20, tall and narrow).
- Fall speed is defined at the pixel level, not the cell level: a piece's front face moves **1 pixel per tick** — continuous, smooth downward motion rather than the shaft version's whole-layer jumps (or the `kFallSubSteps` interpolation trick used to fake smoothness there).
- Controls: **X rotates left, B rotates right** (replacing the shaft version's B=yaw/Y=pitch, single-direction, two-axis scheme with a classic single-axis CW/CCW pair). **Y is now fast drop.** **A stays the menu button.**

This is a full core rewrite, not a tuning pass — `PackitGame.h`'s 3D data model (`kWellX/Y/Z`, `Cell{dx,dy,dz}`, the two rotation axes, the perspective projection in `gameDraw`) doesn't carry over. See "Open questions from the interview" below for what's still unresolved before implementation starts.

### Confirmed design decisions (interview, 2026-09-21)

- **Board**: 9 columns × 8 rows, rectangular cells (~14px wide × 8px tall) filling the entire 128×64 screen — no side panel. Chosen over a square-cell layout (which would've left ~56px of unused width) specifically to fill the wide screen, per the brief.
- **Camera/rendering model** — the key clarification that resolves "keep real 3D, not a pseudo-3D icon": the gameplay grid is genuinely flat (every settled/falling block sits at the *same* fixed depth — the wall is exactly one cube thick), but each individual block still renders with real perspective using the *exact same* per-cube math already built for the shaft version (`cubeWireframe`'s near face + far face + 4 connecting edges). What changes is how a cube's screen position is computed: instead of the old vanishing-point formula that scaled both position *and* size by depth (because depth varied per-cell in the shaft), a cell's (column, row) now maps to screen (x, y) by simple even spacing, like classic Tetris — no scaling, since every cube is the same distance from the camera. The near/far size difference and the diagonal connecting edges are what still read as "real 3D," applied identically to every cell rather than varying with position.
- **Falling piece**: opaque, same rendering as settled blocks — the wireframe-vs-filled distinction from the shaft version is gone entirely.
- **Piece set**: back to the 7 classic tetrominoes (I/O/T/S/Z/L/J).
- **Rotation**: single-axis, classic-style — X rotates left (CCW), B rotates right (CW). No wall-kicks (an illegal rotation is simply rejected), matching the shaft version's philosophy.
- **Fall speed**: normal fall is 1px per tick; Y, held, is a soft drop at 2× speed (not a hard drop — still animated/interruptible, not an instant slam-and-lock).
- **A** stays the pause-menu button; Resume/New Game/Exit carries over unchanged.
- **Fall pacing** (assumed, not explicitly asked): ~100ms per pixel-tick, so a full row takes ~800ms at normal speed, matching the old version's overall pacing — easy to retune once it's playable.
- **HUD** (assumed): no persistent score/next-piece panel during play, since the board now fills the whole screen with no side panel. Score/layers-cleared could surface in the pause menu instead. Revisit once there's something to look at.

### A real open risk, not yet resolved by discussion alone

An 8px-tall row leaves very little vertical room for a visible near/far face size difference — the old shaft used a 12px near-face size for legibility, which simply doesn't fit an 8px cell. The realistic depth offset per cube will be just a couple of pixels. Whether that reads as "real 3D" or just noise at that scale isn't something to reason out further in text — the plan is to build a first pass at these exact dimensions and render a real snapshot to look at, the same way every rendering decision in the shaft version got resolved.

**Resolved by snapshot, 2026-09-21**: the risk didn't materialize. A real 128x64 host render (`firmware/host/packit/`'s `display::snapshot`, `kCellW=14`/`kCellH=8`) shows the inset far face and 4 diagonal connecting edges reading clearly as a "chunky cube" even at that size, both for settled cells and the (now-opaque) falling piece — a 2x2 O-piece and two settled rows are visibly distinct boxes, not noise. `kFarRatio = 0.72` (far face ~72% of near-face size, same `kCamDist`-based 1/depth formula as the shaft version, just evaluated once at z=0/z=1 instead of varying per cell) was the first value tried and looked right; no further tuning pass was needed.

## Flat-board rewrite (2026-09-21, `packit_game` branch)

`PackitGame.h`/`.cpp` were fully rewritten for the design above, replacing the 3D-shaft core entirely (not a tuning pass — the whole data model changed):

- **Board**: `kBoardW=9` x `kBoardH=8`, `kCellW=14`, `kCellH=8`, centered with a 1px margin (`kBoardOffsetX`) since 9*14=126 < 128.
- **Pieces**: the 7 classic tetrominoes (`kPieceI/O/T/S/Z/L/J`), each stored as a 4-rotation-state table of 4 cells inside a 4x4 bounding box (`kShapes[kPieceCount][kRotationStates][kCellsPerPiece]`), the standard SRS spawn layout minus wall-kick data — a rejected rotation just doesn't happen, per the no-wall-kicks decision.
- **Fall model**: `gState.subY`, a float 0..`kCellH`-1, accumulates 1px per `kFallIntervalMs` (100ms) tick, 2px/tick while `GameInput::softDrop` (Y, level-triggered — read every tick, not edge-triggered like every other input field) is held. Only when `subY` crosses a full `kCellH` does the piece's logical `anchorRow` actually advance and get collision-checked (`stepFallPixel` in the anonymous namespace) — movement and rotation stay exactly as discrete as the well grid itself; only the picture moves smoothly.
- **Rotation**: `rotateLeft` (X) and `rotateRight` (B) each just step `rotState` -1/+1 mod 4 and re-check `pieceFits` at the *same* anchor — no kick offsets tried.
- **Rendering, first pass (superseded below)**: the initial cut drew each cell's far face `kFarRatio`-scaled and *centered* inside the near face, both faces' frames always fully visible. A real playtest (2026-09-21) caught two problems this centered/single-pass approach couldn't avoid: with the far face's frame always drawn on top, nothing was ever occluded, so every block read as a transparent wireframe outline rather than a solid cube; and with the far face centered rather than leaning in a consistent direction, there was no visible perspective skew at all — it looked like a bullseye icon, not a receding 3D box.
- **Rendering, second pass (superseded below)**: replaced the centered/transparent version with `nearBox()`/`farBox()` and two full-board draw passes (all far faces, then all near faces) for real occlusion — fixed the "transparent" complaint. But it leaned every cell's far face by the *same fixed pixel vector* (`kLeanX`/`kLeanY`, +3/-3) regardless of board position, reasoning that a true on-board vanishing point makes the effect vanish for cells near the board's own center. A second playtest (2026-09-21) caught the actual consequence of that choice: since the lean never varied, a piece showed *no visible perspective change at all* as it fell or moved sideways — it only ever looked like a static per-cube bevel, never like something moving through a perspective scene.
- **Rendering, corrected (2026-09-21)**: the lean is position-dependent again, but around a vanishing point placed *off the board* (`kVanishCol = kVanishRow = -4.0f`, in grid units) rather than at its center — `leanX(colF)`/`leanY(rowF)` scale with a cell's distance from that off-board point (`kLeanPerCol`/`kLeanPerRow = 0.4px` per grid unit). This keeps the lean genuinely tied to position (a piece visibly leans more as it moves toward the far column/row, confirmed by comparing host snapshots of the same piece at column 0 vs. column 8), while never approaching zero the way a center-board vanishing point did, since no on-board cell is anywhere near -4. `gameDraw`'s two-pass draw order (all `cubeFar()`, then all `cubeNear()`) is unchanged and still what makes occlusion correct regardless of which direction a given cell's lean points.
- **Sign bug, caught by inspection right after (2026-09-21)**: `leanY` negated its result (shift toward the vanishing point, correctly, since it sits above the board) but `leanX` didn't — so the far face shifted *away* from the vanishing point horizontally (rightward, growing with column) instead of *toward* it (leftward), a divergent lean rather than the convergent one real perspective produces. Real perspective always pulls a farther plane toward the vanishing point on every axis, not just some; the fix was adding the same negation `leanX` was missing. Confirmed by snapshot: the exposed top face of a stacked cube now bevels toward the upper-left (both axes pulling the same direction) instead of the previous top-right/divergent look.
- **Rendering, rebuilt as genuine per-vertex projection (2026-09-21)**: asked directly whether the lean/ratio approach was real 3D math or an approximation — it was an approximation (an affine "near box, far box scaled+shifted" model, not a real camera). Replaced with an honest pinhole-camera formula applied per vertex: `screen = principalPoint + focalLen*(world - camPos)/depth`, computed independently for each of a cube's 8 corners (`projectFace()` in the anonymous namespace), with near/far faces filled via `u8g2_DrawTriangle` (2 triangles per quad) rather than `u8g2_DrawBox`, since a true projected face is a quad, not necessarily an axis-aligned rectangle. The first render with this exposed a second real, structural problem, not a coding bug: forcing `kPitchXWorld = kCellW/kCellH = 1.75` (so 9 columns of *stretched* cubes would span 128px at the old `kCellW=14`) meant the same depth ratio that gives one cube a legible near/far size difference also multiplies into a **~16px lateral lean at the board edges** — the diagonal-streak noise an actual snapshot showed. The two effects (per-cube size difference, edge-to-edge lateral lean) are driven by the same camera-distance term in real perspective math; there's no parameter that shrinks one without the other, for a board this many world-units wide. Making cubes true squares (`kPitchXWorld = kPitchYWorld = kCubeWorld = 1`, `kCellW` dropped to 8 in `PackitGame.h`, board now 72px wide, centered with a real margin instead of touching both screen edges) roughly halves the board's total world-space width, which is what actually tames the lean — confirmed by re-rendering: clean square cubes, correct occlusion, a real but modest edge lean that reverses direction between the left and right sides of the board (converging toward a camera centered over the board, `kCamXWorld`/`kCamYWorld = board center in world units`, chosen because centering minimizes the worst-case camera-to-cell distance and therefore the worst-case lean). The one tradeoff: the single board-center cell shows almost no lateral lean, but every cell — center included — still shows the real near/far *size* difference (it depends only on depth, not lateral position), so no cube reads as flat.
- **Fall/lock bug, also caught by the second playtest**: `stepFallPixel()` used to accumulate `subY` toward the *next* row for a full `kCellH` ticks before ever checking whether that row was legal — so a piece visually eased almost a full cell into a row it could never occupy, then snapped back up by nearly a cell the instant it actually locked one row short. That read as "the piece settles a layer above where it appeared to stop." Fixed by checking `pieceFits` for the next row *before* animating into it each tick, not after: if blocked, the piece locks immediately at its current (already-fully-arrived) row, with zero animation overshoot to unwind. This also changed lock timing — a piece now locks the instant it's resting on something, not after one extra `kCellH`-tick wait — so `firmware/host/packit/test.cpp`'s `kTicksToFloorLock` constant and `gameOverTest`'s tick count were updated to match (`(kBoardH-2)*kCellH + 1` and `4+100` respectively; both host-verified).
- The falling piece is opaque, not wireframe — same `cubeFar`/`cubeNear` calls as settled cells, in the same two board-wide passes.
- **Controls**: `PackitScreen.cpp` now maps X→`rotateLeft`, B→`rotateRight`, Y (held, via `inputs.buttons().y`, not an edge)→`softDrop`, A→pause menu; the stick's horizontal axis (via the same `JoyRamp` dominant-axis/repeat-ramp helper) drives `moveLeft`/`moveRight`, and its vertical axis only matters while the pause menu is open, where it drives `menuUp`/`menuDown`.
- **Host tests**: `firmware/host/packit/test.cpp` was rewritten for the new API (8 tests, all passing), and both `make test` and the full `pio run -e replay2026` firmware build succeed against the rewrite as of this pass.
- **Not yet done**: no interactive playtest (only scripted host tests and a static snapshot so far), and the still-uncommitted menu-integration changes from before the redesign (`Screen.h`, `GUI.cpp`, `PackitScreen.{h,cpp}`) are now superseded by this rewrite — nothing has been committed to `packit_game` yet for either the old integration or this new core.

## Brief at kickoff (2026-09-20)

- **Genre**: a Tetris-inspired top-down block-packing game.
- **Presentation**: a new piece appears as a wireframe and descends *away from the camera* — i.e. the fall axis reads as depth, not as "down the screen" the way classic Tetris does.
- **Piece state**: a piece renders as an open wireframe while it's still falling, and becomes opaque/solid once it sets in place.
- **Line clear**: complete rows are removed, and the blocks sitting above a cleared row settle (fall) to fill the gap — the classic Tetris gravity rule, applied to whatever "row" means in this game's geometry (open question below).
- **Controls**: the joystick moves the falling piece left/right/up/down; time (a fall timer) moves it down the depth axis; the four face buttons (`a`/`b`/`x`/`y`) each rotate the piece in a different direction.

This brief reads as more than a re-skinned 2D Tetris: "descends away from the camera" plus a joystick with *both* left/right *and* up/down movement (distinct from the timer-driven fall) plus four independent rotation buttons all point toward a true volumetric piece falling through a 3D shaft, viewed from above — closer to *Blockout*/*Welltris* than to *Tetris* proper. That reading drives the interview below rather than being assumed outright.

## Confirmed design decisions (interview, 2026-09-20)

The brief's "descends away from camera" reading was confirmed: this is a true 3D shaft, not a flat board with a landing flourish.

- **Core structure**: *Blockout*-style. Pieces are volumetric, falling through a rectangular shaft; the camera looks straight down it, so falling reads as shrinking toward a fixed vanishing point rather than sliding down the screen. A "row" is a full horizontal floor-plane slice across the whole footprint — clearing one drops every layer above it down by one, the same gravity rule as 2D Tetris applied to a 3D stack of layers instead of a stack of lines.
- **Well size**: small — a 5×5 floor, originally 8–10 layers deep before the stack tops out (later trimmed to 5, see below). Chosen for legibility on the 128×64 1-bit OLED over spatial complexity, the same "budget-appropriate, classic-era" bias [Helgrind](helgrind.md) and [Vectortank](vectortank.md) both lean on.
- **Piece set**: originally the 7 familiar tetrominoes (I/O/T/S/Z/L/J), each one cube thick; later trimmed to just the 2 free trominoes (I straight, L right-angle bend), see below. They still gain real 3D behavior from rotation, though — a flat piece tipped 90° about a horizontal axis stands up across multiple depth layers instead of lying on one, so "one cube thick" doesn't mean the third dimension is inert.
- **Controls, fully resolved**: the analog stick is pure floor-plane translation (left/right and the joystick's own up/down both move the piece across the 5×5 floor, never the fall axis); the fall timer alone advances the piece along depth; rotation originally lived on all four face buttons (`X`/`B` around the vertical axis, `Y`/`A` around the horizontal), but was later trimmed to just `B`/`Y`, one fixed direction each, freeing `X` and reserving `A` as the badge-wide back/menu button — see "Trimmed to two rotation buttons" below. No roll around the depth axis at all in either scheme — a deliberate cut from the full 3 degrees of rotational freedom a real Blockout piece has.
- **Renderer**: new and purpose-built, not a reuse of [Vectortank](vectortank.md)'s projection/occlusion pipeline. Vectortank's camera roams (yaw, pitch, movement), which is most of why that code is as involved as it is (painter's-algorithm silhouette masking, backface culling, point occlusion); PACKIT's camera never moves, so a fixed depth-to-scale projection toward one constant vanishing point should need none of Vectortank's general-camera machinery.
- **Occlusion is required, not optional**: wireframe is reserved for the single actively-falling piece — every settled layer must draw opaque and occlude whatever's behind it, or a stack more than one layer deep reads as an unreadable tangle of overlapping outlines on a 128×64 1-bit screen. This is a materially simpler problem than Vectortank's occlusion, though: PACKIT's geometry is axis-aligned floor layers stacked along one fixed depth axis rather than arbitrarily oriented boxes seen from a moving camera, so a straightforward farthest-to-nearest layer painter's algorithm (each nearer layer's opaque footprint overdrawing whatever farther geometry sits behind it) should be enough, without needing Vectortank's per-object convex-hull/backface/point-occlusion stack.
- **Game over**: classic topping-out — a new piece fails to spawn because its start position in the shaft is already occupied by settled blocks.
- **Progression**: fixed fall speed, no persistence. No NVS save, no ramping difficulty, no high score — a pure in-session score-attack feel, unlike Vectortank's single anonymous high score.

## First implementation slice (2026-09-20, `packit_game` branch)

`firmware/src/screens/PackitGame.{h,cpp}` is the game-state core: a `bool well[kWellZ][kWellY][kWellX]` grid of settled cells, a falling piece as four `Cell{dx,dy,dz}` offsets from an anchor, and `gameBegin()`/`gameStep()`/`gameStatus()` entry points — no u8g2, no Arduino, not even a draw function yet, one layer earlier than [Helgrind's core/shell split](helgrind.md) (`HelgrindGame.cpp`) which at least draws through u8g2's C API. `firmware/host/packit/` builds this against a small `test.cpp` (plain asserts, no PNG/SDL harness yet since there's nothing to render) — `make test` runs six scripted checks: spawn bounds, wall-blocked movement, the yaw rotation formula, fall-to-lock-to-respawn, a full layer clearing and collapsing correctly, and the top-out game-over condition.

- **Piece shapes**: the 7 tetrominoes are hardcoded as pre-centered offset tables (`kShapes`) so every piece's spawn footprint fits the 5-wide floor at the shared anchor (2,2,0) — e.g. the I piece is `{-1,0,0},{0,0,0},{1,0,0},{2,0,0}`.
- **Rotation is live integer math, not a lookup table**: `rotateYaw()`/`rotatePitch()` apply the exact 90° rotation matrices to whatever the piece's current offsets are (`(dx,dy,dz) -> (dz,dy,-dx)` for yaw, and the X-axis equivalent for pitch), rather than precomputing all reachable orientations per shape. An illegal rotation (would push a cell out of the well or into a settled cell) is simply rejected, matching the "no wall kicks" default from the build-blockers discussion.
- **A real boundary interaction, found by the host test rather than assumed**: a piece sitting at its spawn depth (`anchorZ=0`) can't yaw-rotate if doing so would push any cell to `z<0` — there's no space in front of the shaft's near end to rotate into. `rotateYawMatchesFormulaTest` originally rotated a piece immediately at spawn and got spurious failures until the test was changed to let the piece fall two cells first; the rejection itself is correct collision behavior, not a bug, but it means a player mashing a rotate button the instant a piece appears may find some turns silently do nothing until it's fallen a little. Whether that's worth a spawn-depth buffer is a tuning question for once this is playable, not a blocker.
- **Layer clear**: `clearFullLayers()` scans every `z`, and a full layer's `clearLayer(z)` shifts every shallower layer (`0..z-1`) one step deeper and zeroes a fresh empty layer at `z=0` — the exact analog of a 2D Tetris row clear, applied per depth-layer.
- **Test-support hook**: `debugSetWellCell()` lets the host test poke arbitrary settled cells directly, the same role Helgrind's host-harness `load` script command plays for that game's save fields — necessary here because constructing a specific layer-clear or top-out scenario through legitimate play would otherwise depend on which of the 7 RNG-selected piece shapes happens to spawn.

## Renderer (2026-09-20, `packit_game` branch)


`gameDraw(u8g2_t*, uint32_t)` in `PackitGame.cpp` is now real: the first actual drawing code, using the exact 128×64 1-bit `u8g2_t` the badge will hand it, following [Helgrind](helgrind.md)'s core/shell split exactly (`HelgrindGame.cpp` draws through u8g2 the same way) rather than staying one step earlier as originally planned. It is exercised through the shared [host test harness](../systems/host-test-harness.md), which runs `PackitScreen`.

- **Projection**: one fixed vanishing point at roughly the OLED's center (64,32); each depth layer `z` is the (x,y) floor grid scaled from a 12px near size at `z=0` down to a 3px far size at the last layer, chosen so the near layer's full 5×5 footprint fits inside 128×64 with room to spare on the wide axis.
- **Occlusion, proven out and one bug fixed**: settled cells paint farthest layer to nearest, fully opaque — a nearer filled cell always covers whatever farther geometry shares its ray, the design's layer painter's algorithm. A real snapshot caught a genuine bug in the first version, though: the falling piece's wireframe outline is drawn in the same single "on" color 1-bit has, so an outline landing on top of an already-lit settled cell (a *different* depth's cell that happens to project to the same screen area — the "nearer covers farther" guarantee only holds along a matching address, not between every pair of addresses) became invisible, indistinguishable from the fill beneath it. Fixed by having each piece cell punch out its own footprint (draw color 0) before outlining (draw color 1), so the wireframe reads clearly no matter what's behind it — confirmed by re-rendering the same snapshot.
- **Build**: `firmware/host/packit/`'s Makefile links the vendored U8g2 clib (`gameDraw` lives in the same translation unit the tests build, so `packit-test` needs it to link even though it never calls `gameDraw`).
- **Verified**: `make test` still passes all 6 cases; the projection and the wireframe fix were both confirmed visually on PNGs rendered straight from `gameDraw` (not just reasoned about) before and after the fix.

### A second, more fundamental rendering bug, also user-caught

A user play session on real rendered output found the deeper problem: cubes belonging to the same piece visibly drifted apart from each other as the piece fell into the distance, and a suspicion that the projection was doing "isometric cheating" rather than real perspective — both correct. Two compounding bugs, fixed together:

- `cellSize(z)` was a **linear** interpolation between a near and far size. Real perspective shrinks with `1/depth`, not linearly; the fix (`kCamDist`, solved so `z=0`/`z=kWellZ-1` still land on the same near/far sizes) makes it a true perspective divide, `size(z) = kNearSize * kCamDist / (kCamDist + z)`.
- Every cell's border inset (the gap that keeps adjacent cubes visually distinct) was a **fixed pixel count**, not a fraction of the cell's own size. A fixed inset eats a growing *proportion* of an ever-shrinking cell, so two cubes of the same piece — flush in world space — read as pulling apart on screen as they receded. Fixed by making the inset (`kCellInsetFrac = 0.10`) a fraction of `cellSize(z)`, so the visual gap shrinks in lockstep with the cell instead of swallowing it.
- Also restored the "depth ring" cue the very first (pre-u8g2, SDL-only) mockup had and the u8g2 rewrite dropped: `wellFrame(z)` outlines the well's full 5×5 footprint at a given depth, and `gameDraw` now draws four of these (`{0, kWellZ/3, kWellZ*2/3, kWellZ-1}`, not one per layer — one per layer was tried first and was too dense, reading as visual noise rather than a tunnel) as a backdrop before the settled/falling cells draw over it.
- All three changes verified the same way: rendering real `display::snapshot()` PNGs of a piece at spawn depth and after several fall ticks, confirming the piece's cells stay visibly flush at both depths and the rings read as a receding tunnel rather than clutter.

### Third pass: true wireframe cubes, not filled boxes with a punched-out fix

Proportional insets closed the growing-gap bug but reintroduced the original one: cells still had *some* margin, so a piece still looked like separate floating cubes rather than one seamless polycube, and the settled-cell fill was a flat, featureless slab with no visible cube boundaries at all. The actual design (a user description, restated): pieces are wireframe, not filled, at every depth including the moment they land; each cube's edges and the seams between adjacent cubes in the same shape are single-pixel lines; a locked piece keeps drawing those same edges/seams, but now with real occlusion (a solid fill) behind them, whereas a still-falling piece is genuinely transparent — nothing painted over whatever's behind it, seams or not.

- `cellBox()` dropped the inset entirely — cells now tile the well exactly edge-to-edge, so two adjacent cubes share one boundary line instead of opening a gap that can drift.
- Settled cells: `u8g2_DrawBox` in draw color 1 (the fill, providing occlusion) immediately followed by `u8g2_DrawFrame` in draw color 0 over the same box — a one-pixel black "seam" cut into the white fill along every cell boundary. Where two settled cubes are adjacent the shared seam shows as a grout line separating them; a lone cube's outer seam lands on the already-black background and simply doesn't show, so an isolated locked block still reads as one plain solid tile, not four separately outlined squares.
- The falling piece: no fill at all anymore — just `u8g2_DrawFrame` per cell in draw color 1, letting whatever's underneath (empty well, or a farther settled layer showing through) remain visible. This reopens the earlier "wireframe over an already-lit cell can be invisible" edge case that the discarded punch-out fix had closed, but that trade was made deliberately — the piece is supposed to be transparent, and punching a hole to defeat it was fighting the actual design rather than serving it. u8g2 has no XOR draw mode to guarantee a line's visibility against either background (`u8g2_SetDrawColor` only accepts 0 or 1 — checked against `u8g2_hvline.c`), so this remains a known, accepted limit of 1-bit rendering rather than something with a clean fix.
- Verified visually the same way as the earlier fixes: an O-piece snapshot now shows a flush 2×2 block with one visible internal seam cross, not four separate squares with gaps; settled cells in a mixed scene show individual cube grout lines instead of a blank slab.

One color mistake in that pass: settled cells were drawn face-color-1/seam-color-0 (a white face with a black seam cut into it) — inverted from the intended look. A user catch fixed it to face-color-0/seam-color-1 (black face, white edges/seams), matching the falling piece's white-line wireframe style and reading correctly as an occluding dark solid rather than an inverted white block.

### Fourth pass: real 12-edge cubes for the falling piece, not flat 4-edge faces

A user question ("is the floating piece showing all its edges... or is that an illusion from the low resolution?") led to checking with a real snapshot (a T-piece rotated so one of its four cubes sits a full depth layer behind the other three) rather than guessing — the answer was no edges were being culled (the deeper cube's square showed correctly nested inside the nearer three, visible straight through them since the piece has no fill), but each cube was still only ever drawn as a single flat front-face square: 4 edges, never the 8 more edges a real cube has. The follow-up ask was explicit: every cell should have all 12.

`cubeWireframe(u8g2_t*, x, y, z)` (`PackitGame.cpp`) replaced the falling piece's plain `cellBox`+`DrawFrame` call: it projects a near face at depth `z` and a far face at depth `z+1` (one full unit deeper, since every piece cell is a unit cube) using the same `cellBox()`/perspective math as everything else, draws both faces' 4-edge frames, then connects each near corner to its corresponding far corner with `u8g2_DrawLine` — 4+4+4 = 12 edges, a real wireframe box in perspective rather than a flat square standing in for one. Settled/locked cells keep the flat face+seam treatment from the previous pass (occlusion via a solid fill needs a face, not an open box) — this change is scoped to the still-falling, still-transparent piece only.

Verified visually: a spawn-depth O-piece snapshot now shows each cube's near face, a visibly smaller nested far face one layer behind it, and the four diagonal corner-connecting lines between them — a real 3D box, not a flat outline.

One off-by-one in that pass, caught by a user report ("edges are not meeting at the same vertex pixel"): `cubeWireframe()`'s connecting lines ran from `(nx, ny)` to `(nx+nw, ny+nh)`-style corners, but `u8g2_DrawFrame(x, y, w, h)` actually draws its right/bottom edge at `x+w-1`/`y+h-1` (confirmed in `u8g2_box.c`'s `u8g2_DrawHVLine` calls), one pixel short of `x+w`/`y+h`. Every connecting line's endpoint was landing one pixel past where its own face's frame was actually drawn, so each cube's corner showed as two separate points instead of meeting at one vertex. Fixed by computing `nx2 = nx+nw-1` (etc.) for the far corners of both faces before drawing the 4 connectors. Reverified with the same spawn-depth snapshot — corners now meet at a single pixel.

### Fifth pass: shallower well, and smoothed fall animation

With true 3D wireframe cubes now rendering (previous pass), the full 8-layer shaft read as too visually dense at 128×64 — a user call to "trim it back a little" cut `kWellZ` from 8 to 5. `cellSize()`'s perspective-divide formula re-derives `kCamDist` from `kWellZ` automatically, so the near/far sizes (`kNearSize`/`kFarSize`) stayed the same; the well is just shallower now, not rescaled.

The same request also asked to slow the piece's actual drop rate *and* smooth its motion between layers, "keeping the delay between movements the same." Both come from one mechanism: `kFallSubSteps = 3` (public in `PackitGame.h`) means a real fall step (the one that can lock/clear/spawn) now only happens once every 3 ticks of the fall timer, not every tick — `GameState` gained a `fallSubStep` counter (0..2) that `gameStep()` advances every `kFallIntervalMs` (unchanged) and only calls `stepFall()` when it wraps back to 0. This *is* "keeping the delay the same": each tick still fires at the same interval it always did, there are just three of them per real layer now, which triples the time a real drop takes (the "slower" part) for free. `gameDraw()` uses the two ticks in between to interpolate the falling piece's rendered depth (`animZ = anchorZ + fallSubStep/kFallSubSteps`, fed into `cubeWireframe()`, which now takes a `float z`) smoothly toward the next layer, while `anchorZ` itself — and therefore all movement/rotation collision — stays exactly as discrete and snapped as before. Only the picture eases; the grid logic doesn't know sub-steps exist.

This changed how many `gameStep` ticks the host tests need to reach a real fall: `rotateYawMatchesFormulaTest`, `fallLockSpawnTest`, `layerClearTest`, and `gameOverTest` all previously assumed one tick = one real layer and now multiply their tick counts by `kFallSubSteps`. Verified: all 6 tests still pass; a scratch snapshot confirmed `anchorZ` stays at 0 through the first 2 sub-ticks and only advances to 1 on the 3rd, while the rendered piece visibly shrinks a little at each intermediate tick — the interpolation is real, not just reasoned about.

### Sixth pass: four layers, two trominoes

Still too visually dense: "trim it down more." Two more cuts, both purely reductions of existing parameters, no new mechanics:

- `kWellZ` cut again, 5 → 4.
- The 7-tetromino piece set replaced with just the 2 free trominoes — `kPieceI` (straight, 3 cells in a row) and `kPieceL` (a single right-angle bend) — `kPieceCount` now 2, `kCellsPerPiece` now 3. `kShapes` shrank to a 2-row table; every other piece of code (`GameState::cells`, `pieceFits`, `tryRotate`, `spawnPiece`, `gameDraw`'s piece loop) already sized itself off `kCellsPerPiece` rather than a hardcoded 4, so this was purely a data change, not a logic change.
- `firmware/host/packit/test.cpp`'s `gameOverTest` recomputed its "block every spawn footprint cell, whatever piece shows up" union for the new 2-shape set: `(1,2),(2,2),(3,2)` from the I-tromino plus `(2,2),(3,2),(2,3)` from the L-tromino, a 4-cell union instead of the old 7-shape, 8-cell one.

Verified: all 6 host tests still pass with the new constants, and a snapshot at spawn depth shows a clean 4-layer set of depth rings (down from the earlier 8) with the (now 3-cube) piece's wireframe legible against them.

### Seventh pass: trimmed to two rotation buttons, and a real pause menu

The 4-button rotation scheme (X/B for yaw CW/CCW, Y/A for pitch CW/CCW) left no button free for the badge-wide back/menu convention every other game uses (Helgrind: "A opens menu"). With the piece set down to 2 trominoes, a user call cut rotation to just `B` (yaw) and `Y` (pitch), each a single fixed direction rather than a CW/CCW pair — repeatedly pressing the same button still reaches every reachable orientation, just possibly with more presses. `GameInput` dropped the `x` field entirely; `a` was repurposed from "pitch CCW" to "open/back out of the pause menu."

This needed real pause-menu state in the core, not just a control remap, so `PackitGame.cpp` gained:

- A `Mode` enum (`kPlay`/`kMenu`) and `menuSelect` in `GameState`, exposed read-only via `GameStatus::menuOpen`/`menuSelect`.
- `resetGame()`, factored out of `gameBegin()` so the menu's New Game action and a fresh `gameBegin()` share the exact same seed/spawn logic instead of duplicating it.
- `resumePlay()`, which resets `lastFallMs` (and `fallSubStep`) to `now` on Resume or A-as-back — without this, wall-clock time spent sitting in the menu would read as elapsed fall time and the piece would drop several layers the instant play resumed.
- `gameStep()`'s signature changed from `void` to `bool`, mirroring Helgrind's `gameStep` exactly: it returns true when Exit is confirmed, the signal a future `PackitScreen` shell would use to pop back to the main menu. While `mode == kMenu`, `gameStep` reads `moveNear`/`moveFar` as menu-navigation up/down (wrapping) instead of floor movement, `B` confirms the highlighted item (Resume/New Game/Exit — `PauseMenuItem` in the header), and `A` always backs out to Resume regardless of what's highlighted, never confirming a selection by itself.
- `gameDraw()` draws the frozen well/piece underneath as normal, then — Helgrind-style — clears and frames a small panel on top listing the three options with a `>` marking the current selection, using `u8g2_font_6x10_tr` (the same font Helgrind's host window help panel uses).

Verified: a new `menuTest()` in `test.cpp` (7th host test) opens the menu, confirms movement input is ignored while it's open, walks the selection forward through all three items (checking the wrap from Exit back to Resume) and backward (checking the reverse wrap), confirms A backs out without confirming, confirms New Game via B actually clears a well cell (not just closes the menu), and confirms Exit via B returns `true`. A real snapshot after opening the menu and moving the selection to New Game showed a clean, legible panel with the frozen board visible underneath and the `>` cursor on the right line.

On the reported "regression in the rotation buttons": nothing in `rotateYaw`/`rotatePitch`/`tryRotate` itself had changed since they were added, and the host keyboard mapping (`window.cpp`) reads as intended — no specific bug was found in review. It's plausible what read as a regression was really the friction of the old 4-button CW/CCW scheme now colliding with the need for a back button; the 2-button redesign here supersedes that scheme entirely, so if the feel is still off after this pass it's worth a fresh, specific report rather than assuming the old code was actually broken.

## PackitScreen: wired into the main menu (2026-09-20)

The core+host slice above was committed (`62ec2e1` on `packit_game`), then `PackitScreen.{h,cpp}` filled in the shell, following [Helgrind](helgrind.md)'s `HelgrindScreen` pattern exactly: a thin adapter between the badge (`Inputs`, `millis`, `oled`) and the firmware-free core, with no logic of its own beyond input translation.

- **Screen registration**: `Screen.h` gained `kScreenPackit` in the `ScreenId` enum (after `kScreenVectortank`); `ui/GUI.cpp` registers a `static PackitScreen sPackit` and adds a `"PACKIT"` tile to `kCuratedMenuItems`, reusing `AppIcons::games` — the same icon [Helgrind](helgrind.md) and [Vectortank](vectortank.md) (menu-labeled "GRENADA") both use, rather than commissioning new art.
- **Stick-to-discrete-grid translation**: `PackitGame`'s `GameInput` wants edge-triggered one-cell-per-press movement, but `Inputs::joyX()`/`joyY()` are continuous analog. `PackitScreen::handleInput` reuses `JoyRamp` (`screens/JoyRamp.h`) — the same dominant-axis-plus-repeat-ramp helper `GridMenuScreen` uses to turn the stick into cursor steps — copying its exact deadband/axis-priority logic rather than inventing a second way to do the same job.
- **Button mapping**: `B`/`Y` (`Inputs::edges().bPressed`/`yPressed`) feed the core's two rotation buttons directly; `A` (`aPressed`) feeds the core's menu-open/back button. No stick-vs-button ambiguity issues since PACKIT's rotation buttons are the semantic pad, not the analog stick.
- **Force-sleep**: `suppressesForceSleep()` returns true, matching Helgrind/Vectortank's reasoning — `Y` is the physical UP button, and PACKIT uses it as a live in-game control (pitch rotation), so the system's hold-UP-5s force-sleep gesture would otherwise fight it.
- **No persistence, no LED matrix use**: `onEnter` just calls `gameBegin(millis())`; there's no `onExit` override, no NVS reads/writes, and no `ledAppRuntime` override — all matching the design's confirmed "fixed speed, no persistence" decision and the still-undecided LED matrix question below.
- **Verified**: a full `pio run -e replay2026` firmware build succeeds with `PackitScreen.cpp.o`/`PackitGame.cpp.o` compiled and linked in (confirmed both object files exist in `.pio/build/replay2026/src/screens/`), flash/RAM usage well within budget (61.2%/36.6%). The 7 host tests still pass unaffected, since none of this integration touches `PackitGame.{h,cpp}` itself.

## Lock delay: a half-second grace window to slide a placed piece (2026-09-21)

Interactive playtesting on real hardware surfaced a feel problem the scripted host tests couldn't catch: `stepFallPixel()` locked a piece the instant its next row was blocked, in the same tick that a same-frame slide input arrived, so a slide timed right as the piece landed was silently eaten. `PackitGame.cpp` now gives a piece `kLockDelayMs` (500ms) to hover at its resting row — still fully movable/rotatable, `pieceFits` re-checked fresh every tick — before `finishLock()` (the extracted former body of the immediate-lock branch: lock, clear rows, spawn next) actually runs. `GameState` gained `locking`/`lockDeadlineMs`; `stepFallPixel` now takes `now` to stamp the deadline, and `gameStep` checks it against `now` once per call, independent of the `kFallIntervalMs` fall-tick cadence, so the hover is wall-clock time rather than tick-count time. If a slide during the hover moves the piece off its ledge, the very next `stepFallPixel` call finds `pieceFits` true again and resumes falling normally — no separate "unstick" check needed, since the fit test already runs fresh every tick.

This changed lock timing for every test that drives a piece to the floor, so `firmware/host/packit/test.cpp` switched from single big `gameStep` time-jumps to a `stepTicksTo()` helper that steps in real 100ms increments (matching how the firmware actually calls `gameStep`, once per frame) — a single jump can't observe the deadline, since it's computed relative to the `now` passed into the same call that sets it. `fallLockSpawnTest`, `rowClearTest`, and `gameOverTest` all now run to `kTicksToFloorLock * 100 + kLockDelayMs` (or the local equivalent) instead of stopping right at the old immediate-lock point. A new test, `lockDelaySlideTest`, drives a piece to the floor, confirms it's still hovering (not locked) at the old immediate-lock deadline, applies a slide, confirms the piece moved rather than having already locked at its pre-slide column, then drives past the real deadline and confirms it locks.

## Game over now opens the pause menu, minus Resume (2026-09-21)

Also found in the same playtest pass: topping out (a spawn that doesn't fit) used to just freeze `gameStep` behind its `if (gState.gameOver) return false;` guard with the board still on screen and no way to do anything — no menu, no restart, nothing short of leaving the screen. `finishLock()` now sets `gState.mode = Mode::kMenu` (with `menuSelect = kMenuNewGame`) in the same branch that sets `gState.gameOver = true`, so the pause menu opens automatically the instant the game tops out, no A press needed. Since there's no live game left to resume into, Resume is hidden rather than just disabled: a new `stepMenuItem()` helper skips over `kMenuResume` when advancing the selection in either direction whenever `gState.gameOver`, `gameDraw()`'s menu-panel loop skips drawing that row entirely (renumbering the remaining rows so there's no gap), and `A` — normally the "cancel back to Resume" shortcut — is a no-op in this state rather than resuming a game that no longer exists. New Game and Exit both still work unchanged from the game-over menu. `gameOverTest` in `test.cpp` now checks all of this: the menu auto-opens on New Game (not Resume), A doesn't close it, up/down navigation wraps straight between New Game and Exit, and confirming New Game clears both `gameOver` and `menuOpen`.

All 9 host tests and the full `pio run -e replay2026` build pass.

## Dotted border rules flush against the board edges (2026-09-21)

A cosmetic pass added a single-pixel-dotted vertical rule immediately outside each side of the board (`gameDraw()`, one line per side, `u8g2_DrawPixel` every other row) to visually mark the play-field boundary against the otherwise-blank side margins (`kBoardOffsetX` is 28px on a 9-column, 8px-cell board centered in 128px). The rules sit at `kBoardOffsetX - 1` and `kBoardOffsetX + kBoardW*kCellW` — flush against the board, zero margin, one column outside it rather than centered in the margin (a first pass centered them in the margin and was corrected after review to sit right at the edge instead).

## Game always opens on the pause menu, not straight into play (2026-09-21)

`gameBegin()` previously called `resetGame()` and left `mode` at its default `Mode::kPlay`, so a piece started falling the instant the screen opened. It now forces `mode = Mode::kMenu` (`menuSelect = kMenuResume`) right after `resetGame()` spawns the first piece — the same pause menu used mid-game, just opened automatically at start rather than requiring an A press. Since `resetGame()` already spawned a piece, selecting Resume (or pressing A, the usual back/cancel shortcut) picks play up immediately, exactly like un-pausing.

This changed test setup broadly: `firmware/host/packit/test.cpp` gained a `beginPlaying(now)` helper (`gameBegin(now)` + a synthetic A press to resume) that every gameplay-focused test now calls instead of `gameBegin()` directly, since they all assume play starts immediately. `menuTest()` itself was rewritten to assert the new starting state (`menuOpen` true, `menuSelect == kMenuResume` right after `gameBegin()`) rather than asserting the menu starts closed, and to re-open the menu explicitly (via A) partway through to exercise the mid-play pause path the way the test used to exercise the initial state.

Verified: all 9 host tests pass with the new helper and rewritten `menuTest`, and the full `pio run -e replay2026` build succeeds. Flashed to hardware and confirmed the badge now opens PACKIT on the pause menu instead of a live falling piece.

## Stick-down didn't soft drop on real hardware (2026-09-21)

A hardware playtest found the joystick's down push did nothing during play — only the dedicated `Y` button soft-dropped. The cause: `PackitScreen::handleInput`'s `dir`/`joyRamp_` machinery only tracks the stick's *dominant* axis and turns it into an edge-triggered discrete step (used for `moveLeft`/`moveRight` during play, `menuUp`/`menuDown` in the pause menu) — during play, a downward push simply had no discrete action to map to, so it was silently dropped. Fixed by reading the raw vertical deadband check directly for `softDrop` (`in.softDrop = inputs.buttons().y || dy > kJoyDeadband`), independent of `joyRamp_`. Verified with a full `pio run -e replay2026` build and reflashed to hardware.

## Remaining open questions

- **1-bit "opaque" texture**: settled cells currently draw as flat filled boxes; whether a depth cue beyond size alone (a dither pattern per layer, say) would help legibility on real hardware is untested.
- **Piece preview**: whether the next piece is shown ahead of time (standard in modern Tetris, absent from the original) is undecided.
- **HUD/footer**: whether PACKIT follows Helgrind/Vectortank's status-band footer convention (`OLEDLayout::kFooterTopY..kScreenH`) and what it would show, given there's no persistent score or HP to display.
- **LED matrix**: `PackitScreen.cpp` has no matrix override, so the ambient animation keeps running. A score display was prototyped for the old host viewer and removed as unused; [Vectortank's](vectortank.md) radar is the pattern if one is wanted.
- **Spawn-rotation buffer**: whether the near-spawn rotation restriction found above is worth changing once the game is playable and this can be felt rather than reasoned about.
