# Storage Model: NVS, FATFS, app0

The badge splits persistent state across three tiers with very different survival guarantees, and picking the wrong one is the most common way to accidentally lose a user's data. The full mental model — including the complete NVS namespace table and every flash-path-vs-tier truth table — is maintained in `firmware/docs/STORAGE-MODEL.md`; this page covers the shape of the rule and why it exists, and should be read alongside that file rather than instead of it.

## The three tiers

- **NVS** (`badge_*` namespaces) holds badge identity, WiFi credentials, contacts, the Badge Info contact card, `badge.kv` game saves/scores, asset version stamps, and menu order. It survives every flash type, including a full factory reflash.
- **FATFS** (`/lib`, `/apps`, `/docs`, `/images`, …) holds Python source, docs, and images. It survives a firmware-only flash but is wiped by a `fatfs.bin` reflash, `uploadfs`, or a `badge_sync --clear-extras` pass.
- **app0** (the firmware binary) embeds only what's under `firmware/initial_filesystem/lib/` and `firmware/initial_filesystem/matrixApps/` — the fixed `BAKE_DIRS = {'lib', 'matrixApps'}` set in `firmware/scripts/generate_startup_files.py`. Those five files (`badge_app.py`, `badge_kv.py`, `badge_ui.py`, `LED.py`, `led_runtime.py`) are the survival floor: with nothing else on FATFS, the badge can still boot to its menu, run a Python REPL over JumperIDE, and re-sync the rest of the filesystem from there. `provisionStartupFiles()` restores any bake-set file that's missing or hash-mismatched at boot, with user-edit detection so a developer's modified copy isn't clobbered — but it never creates files outside the bake set.

The rule of thumb that falls out of this: **code** goes on FATFS and ships via `firmware/data/` (the gitignored build mirror of `firmware/initial_filesystem/`, regenerated by `scripts/generate_startup_files.py` as a PlatformIO `pre:` step — never hand-edited); **state** goes in NVS via `badge.kv` so it survives reflashes. A Python app writing high scores to `open("/save.json", ...)` on FATFS will see that file vanish on the next factory image or `uploadfs`; the same score written through `badge.kv_put(...)` (or the `/lib/badge_kv.py` wrapper) lives in the `badge_kv` NVS namespace and survives.

## Why this matters beyond app development

Every flashing path in this repo is defined by which of these three tiers it touches. [Ignition](../systems/ignition.md)'s firmware-only build+flash leaves FATFS and NVS untouched; its `--factory-image` path is a full esptool batch write that replaces app0 and FATFS but still preserves NVS; [`badge_sync.py`](badge-sync.md) is the one tool that can update FATFS surgically (diff-and-push specific files) without going through either a firmware or factory reflash. Understanding which tier a given workflow step touches is the fastest way to predict whether a given operation is safe to run against a badge with real attendee data on it.

Adding a new NVS namespace should follow the existing `badge_` prefix convention documented in `firmware/docs/STORAGE-MODEL.md`'s namespace table, so each subsystem gets its own iterator scope and namespace collisions stay impossible by construction.

## FATFS writes go through one lock, for a documented reason

The on-flash FATFS driver (`oofatfs`) is built with `FF_FS_REENTRANT=0`, so it has no internal thread safety of its own — yet [Boops](badge-boops.md), `BadgeInfo`, `BadgeConfig`, `StartupFiles`, and the FileBrowser (an OLED settings editor and file viewer activated by holding both A and B for about a second) all hit the same FATFS instance from independent tasks and cores. `firmware/src/infra/Filesystem.h` documents the concrete symptom that motivated its `IOLock` (a recursive mutex every direct `f_*` call is expected to wrap, plus atomic `writeFileAtomic`/`readFileAlloc`/`removeFile` helpers built on top of it): a high-frequency writer racing a slower one inside FATFS's directory-cluster bookkeeping produced JSON body bytes showing up as fake 8.3 directory entries after a heavy write window. New code that needs FATFS access should use the atomic helpers rather than raw `f_*` calls.

## Settings live in two places, with a guard against one specific past bug

Runtime-tunable settings (`Config` in `firmware/src/infra/BadgeConfig.h`) are primarily a human-readable INI file, `settings.txt`, on FATFS — `loadFromNvs()` supplies early defaults before FATFS is mounted, `loadFromFile()` takes over once MicroPython mounts it, and the FileBrowser's live editor calls `saveToFile()` on exit. WiFi credentials are the one part of `Config` that lives in NVS proper rather than the INI file (up to four saved network slots, `ui_wifi_ssid_<n>`/`ui_wifi_pwd_<n>`, decoded from an obfuscated blob at load time and re-scrambled on save). The fixed-size settings array (`kMaxSettings = 64`) carries a `static_assert` enforcing it stays `>= kCount`, added after a real incident where a too-small array silently truncated writes and let out-of-bounds reads/writes from `get()`/`apply()` corrupt adjacent `Config` members — the failure mode was `log_notify` reading back a huge garbage value and crashing the badge.
