# Vectortank: Native Wireframe Vector Game

`firmware/src/screens/VectortankScreen.{h,cpp}` is a Battlezone-style wireframe demo — driving camera, box "artifacts," and a fixed-arc fire weapon — reachable from the main menu's "VECTOR" tile (`kScreenVectortank`), sitting alongside the still-placeholder "HELGRIND" tile from the [Doom removal](doom.md). Unlike most of the [screen stack](gui-screen-stack.md), it implements `render()`/`handleInput()` directly rather than subclassing `ListMenuScreen`/`ModalScreen`/`GridMenuScreen` — it's a real-time game loop (camera movement, projectile physics, particle simulation) with no list/modal/grid shape to inherit.

## It started as a MicroPython app, and that comparison found a real bug

The badge originally shipped a MicroPython prototype (`community_apps/vectortank/`) to test whether the hardware could do vector rendering at all, then benchmarked it against a hand-written native C++ port. The first head-to-head showed almost no speed difference between interpreted Python and native C++ — which didn't match the ESP32-S3's real hardware FPU (`cosf()` at 121 cycles vs. 2,377 on an FPU-less core, per Espressif's own benchmark). The cause was a genuine bug shared by *both* paths: `u8g2_DrawLine()` takes `u8g2_uint_t`, which is `uint16_t` on 32-bit targets, and `oled::drawLine()` (`firmware/src/hardware/oled.cpp`) passed signed `int` straight through with no clamping — an off-screen negative coordinate (e.g. `-50`) silently wrapped to a huge unsigned value (`65486`), turning what should have been a no-op into a multi-thousand-step Bresenham walk. Fixed with Liang-Barsky line clipping inside `oled::drawLine()` itself (not per-caller), which corrected *every* `drawLine` caller in the firmware, not just this screen. With that fixed, native C++ measured ~55x faster than the Python path at the draw-phase level (0.067 ms/artifact vs. ~3.7 ms/artifact at 64 artifacts); the badge maintainer concluded native C++ was required, and the Python app plus its benchmark harness (`firmware/scripts/vectortank_bench.py`) were deleted — only the native `VectortankScreen` shipped.

The renderer is deliberately plain `float` math with no SIMD/`esp-dsp`: the ESP32-S3's PIE "vector" instructions are int8/int16-only and don't help 3D float math, so the actual win is the hardware FPU plus removing MicroPython's interpreter overhead, not any vector unit — the code comments call this out explicitly to head off the obvious misreading of "native C++ beat Python" as being about SIMD.

## The control scheme is an FPS walker, not an independent turret, because of the button budget

The badge has exactly one 2-axis stick and 4 physical buttons — `confirm`/`cancel` are semantic aliases permanently paired over the `down`/`right` buttons (see `Inputs::updateSemanticAliases()`), not extra inputs. That's not enough budget for a Battlezone-style independent turret (body + turret + aimable arc + fire + back as five separate controls), so aim direction equals move direction, and the fired shot's arc is **fixed**, not player-aimed — removing the control conflict an aimable arc would have had with the stick's forward/back axis. Left/right (`x`/`b`) strafe the camera perpendicular to its facing without changing yaw; because that claims the `right` button, fire and back deliberately read the **raw** `upPressed`/`downPressed` edges rather than the `confirm`/`cancel` semantic layer — going through that layer would fire-or-pop on every strafe-right depending on the user's confirm/cancel-swap setting, since `right` is always one half of that pair regardless of the swap.

An early version of `Camera::toCameraSpace()` rotated world coordinates by `-yaw` while `Camera::move()`'s forward vector used `+yaw` — they silently disagreed by a factor of 2×yaw, so turning felt plausible for small angles but fired shots (which reuse the movement forward vector) drifted off from where the camera was actually looking. Fixed by rotating both by the same `+yaw`.

## Projectiles have a fixed lob arc and shrink to a pixel on landing

`kShotSpeed`/`kShotLift`/`kGravity` define a constant-arc trajectory (no player-controlled pitch, per the control-budget constraint above); a shot's on-screen size scales with its current altitude relative to the arc's analytic peak height, shrinking to a single pixel exactly as it reaches the ground. Hitting an artifact's footprint (x/z within half-width, current height under the box's height) marks it destroyed and stops it from drawing or colliding again — there is currently no win condition or respawn once all artifacts in a play session are destroyed; the scene just stays empty until the screen is re-entered.

## Particles are explosion bursts only, not ambient dust

An earlier version kept a pool of particles drifting continuously near the camera as background atmosphere. That was replaced with an explosion-only model: the fixed-size particle pool (`kMaxParticles = 64`) sits entirely inactive until `spawnExplosion()` activates up to `kExplosionParticleCount = 14` slots at once, scattering them outward under their own small gravity with a short (~0.25-0.55s) lifetime before going inactive again. Both an artifact hit and an unclaimed shot's ground impact trigger a burst, so every shot resolves in a visible particle effect somewhere.

## Hidden-surface removal, without a per-pixel depth buffer

The wireframe renderer originally drew every visible edge of every artifact unconditionally, which meant objects could be seen straight through each other — a farther box's edges showed right through a nearer one, a box showed through its own far side, and a fired shot or explosion stayed visible even when a box was directly between it and the camera. The badge has no spare RAM/CPU budget to justify a full 128×64 per-pixel z-buffer for this, so `drawScene()` (`firmware/src/screens/VectortankScreen.cpp`) instead uses three cheaper techniques stacked together, all reusing per-artifact state computed once per frame in a `static ArtifactRenderState states[kMaxArtifacts]` cache (so testing particles/projectiles against every artifact doesn't repeat each artifact's 8-vertex `toCameraSpace()` transform):

1. **Inter-object masking via painter's algorithm.** `drawScene()` depth-sorts artifacts farthest-to-nearest (by `minVisibleDepth()`, the nearest projected-vertex camera-space `z` — a proxy for "how close is this box's front surface") and, for each one nearest-last, fills its projected silhouette in the background color (`fillArtifactSilhouette()`) before drawing its edges. This is the same trick classic vector arcade games used for hidden-line removal on hardware that couldn't z-buffer per pixel. The silhouette itself is the convex hull (`convexHull()`, Andrew's monotone chain over up to 8 projected vertices) of the box's screen-space vertices, Sutherland-Hodgman–clipped to the screen rect (`clipPolygonToScreen()`) before being fan-triangulated into `oled::fillTriangle()` calls — the clip matters because `u8g2_DrawTriangle()` takes signed `int16_t` (confirmed by reading `u8g2_polygon.c`, unlike the `u8g2_uint_t`/`uint16_t` that caused the `oled::drawLine()` overflow bug described above), but an unclipped fill would still distort the fill shape at the screen edge instead of masking correctly.
2. **Self-occlusion via backface culling.** Painter's-algorithm silhouette fill only ever masks *other*, farther artifacts — it does nothing about a single convex box's own far edges, which were still drawing straight through its near faces. `computeFaceVisibility()` tests each of a box's 6 axis-aligned faces with one dot product against the camera's world position (no trig — the faces don't rotate with the camera, only the box's fixed geometry matters), and `drawArtifactEdges()` skips any of the 12 edges (via the `kEdgeFaces` adjacency table) where both adjacent faces point away from the camera.
3. **Point occlusion for particles and projectiles.** Fired shots and explosion particles used to draw unconditionally after the whole scene, so a shot could still be seen through a box directly in front of it. `occludedByArtifact()` tests each particle/projectile's screen position and camera-space depth against every artifact's cached silhouette hull (`pointInConvexHull()`, a consistent cross-product-sign test) and nearest depth, skipping the draw if some artifact is both closer to the camera and covers that screen point.

All three checks are cheap relative to the per-vertex trig that already dominates the frame: `computeFaceVisibility()`'s 6 dot products are a small fraction of the 16 hardware-FPU `sinf`/`cosf` calls already spent projecting one box's 8 vertices, so backface culling in particular is expected to be immeasurable against the frame budget — if the render loop ever does get trig-bound, caching `cosf(yaw)`/`sinf(yaw)` once per frame instead of recomputing them inside every `Camera::toCameraSpace()` call (currently once per vertex, across every artifact and every particle/projectile) is the bigger lever, not this occlusion work.

## Background: a horizon line and a bearing-locked mountain skyline

Before the occlusion pass above existed, the scene had no depth cue behind the artifacts — just whatever was left on the display. `drawScene()` now opens by calling `drawHorizon()` and `drawMountains()`, which draw a flat horizon line and a jagged distant-mountain silhouette *before* the artifact painter's-algorithm loop, so a nearer artifact's silhouette fill (which clears in the background color) correctly erases the background behind it exactly like it already erases farther artifacts.

The horizon is a single horizontal line at `kHorizonY = kScreenH / 2` (screen row 32), not something recomputed per frame: `Camera` never pitches and the eye height is a fixed `1.0f` in `toCameraSpace()`, so a point at eye height always projects to screen-center regardless of yaw — the horizon's screen position is a constant, not a render-time calculation.

The mountains are the part that has to respond to turning. `mountainHeightPx()` is a fixed sum of three sine waves at incommensurate frequencies over *world-space bearing angle*, not screen column — `drawMountains()` converts each screen column `x` to a bearing via `cam.yaw + atan2f(x - kScreenW/2, kFovScale)` (the same `kFovScale` used by `project()`) before sampling it. Driving the skyline off world bearing rather than screen position is what makes it scroll correctly as the camera turns instead of dragging along as a static image painted onto the screen; because the height function is periodic in angle, the skyline also matches up seamlessly after a full 360° turn with no seams or resets.

## Taking over the LED matrix: a player-oriented radar with a strobe override

The badge's 8x8 ambient LED matrix normally free-runs its own animation (or a MicroPython matrix app) via [`LEDAppRuntime`](led-app-runtime.md), completely independent of whatever's in front on the OLED — a second display surface Vectortank was leaving idle. `VectortankScreen::onEnter()` now claims it with `ledAppRuntime.beginOverride()` and hands it back in `onExit()` with `endOverride()`, the same refcounted contract `SettingsScreen` already uses for its LED-brightness live preview (`firmware/src/screens/SettingsScreen.cpp`'s `enterEditMode()`/`exitEditMode()`) — refcounted so it nests safely if something else calls `beginOverride()` too, rather than one caller's `endOverride()` prematurely restoring ambient mode out from under the other.

Once claimed, `drawRadar()` (`firmware/src/screens/VectortankScreen.cpp`) draws alive artifacts as blips positioned by bearing and range relative to the camera, reusing the exact same rotation `Camera::toCameraSpace()` uses so that "forward" always lands toward row 0 of the matrix regardless of world yaw — the radar turns with the player instead of the player's marker moving around a fixed compass, the same "bearing-locked, not screen-locked" design as the mountain skyline above. `VectortankScreen::render()` throttles the matrix write to `kRadarIntervalMs` (100ms, matching `LEDAppRuntime::kDefaultDelay`) rather than the OLED's own frame rate, since each `LEDmatrix::setPixel()`/`drawMask()` call is a synchronous I2C write to the IS31FL3731 driver, not a buffered framebuffer flip.

The radar isn't the only thing the matrix shows: a shot that explodes within `kStrobeTriggerRangeWorld` (6 world units) of the camera sets `gStrobeStartMs = millis()`, and for the next `kStrobeDurationMs` (250ms) `drawRadar()` skips the radar draw entirely and instead flips the whole panel full-on/full-off every `kStrobeIntervalMs` (40ms) via `drawStrobe()`. `render()` also shrinks its own write interval to `kStrobeIntervalMs` while a strobe is active, since the radar's normal 100ms cadence is too slow to render a 40ms flicker. This makes the matrix multi-function without a mode enum or state machine: the strobe is a temporary, self-expiring override of the radar in exactly the shape `LEDAppRuntime`'s own override/restore contract takes one level up (VectortankScreen overrides the ambient matrix; the strobe overrides VectortankScreen's own radar), just implemented as "is `now` still inside the last strobe's window" rather than an explicit begin/end pair, since a strobe never needs to nest or be cancelled early.

After first testing on-device, `kRadarRangeWorld` was doubled from 16 to 32 world units so the radar reads artifacts about twice as far out — the same blip math above, just a wider world-to-cell scale factor.

## Opting out of the global force-deep-sleep long-press

`SleepService::service()` (`firmware/src/hardware/Power.cpp`) force-enters deep sleep whenever `inputs_->heldMs(0) >= kForceDeepSleepHoldMs` (holding UP for 5 seconds) — a global capture with no per-screen awareness, since `SleepService` never held a pointer to `GUIManager` or the active `Screen`. That collided with Vectortank's own raw-edge fire button (also UP): holding UP to keep firing for 5 seconds would also put the badge to sleep mid-game.

Rather than special-case Vectortank inside `SleepService`, `Screen` (`firmware/src/screens/Screen.h`) gained a new virtual, `suppressesForceSleep()`, defaulting to `false` — the same idiom as the existing `needsRender()` opt-out and `GUIManager::nametagSuppressedForCurrentScreen()`'s hardcoded screen-ID check, generalized into a proper per-screen hook instead of another hardcoded ID comparison. `SleepService` gained a `bindGUI(GUIManager*)` setter and a `gui_` member; `main.cpp` calls `sleepService.bindGUI(&guiManager)` right after `sleepService.bindInputs(&inputs)`. `service()` now reads `gui_->currentScreen()->suppressesForceSleep()` before honoring the long-press, and `VectortankScreen::suppressesForceSleep()` overrides to `true`. Every other screen is unaffected — the accessor is optional (an unbound `gui_` behaves exactly like before this change), and no other screen currently overrides the new virtual.

## Back opens a pause menu instead of exiting

Back (the raw `downPressed` edge — see the control-scheme section above for why it isn't the semantic cancel layer) used to call `gui.popScreen()` directly, so a stray back-press mid-game lost the run with no confirmation. `VectortankScreen` now has a `paused_` member (reset to `false` in `onEnter()`); a back-press while playing sets `paused_ = true` and `render()` draws `drawPauseMenu()` (`firmware/src/screens/VectortankScreen.cpp`) — a "PAUSED" box with a single "Exit" row — over a frozen frame of the scene, rather than swapping to a separate screen, so the game visibly still exists underneath.

While `paused_` is set, `handleInput()` takes a completely different branch: it skips camera movement, particle/projectile stepping, and firing entirely (the game is frozen, not just visually obscured), and remaps input to menu navigation — back (`downPressed`) closes the menu and resumes play, and the device's "B" selection button (`edges().rightPressed`, physically the same button as strafe-right during play — see `Inputs.cpp`'s `buttons().b`/`buttons().right` aliasing) selects Exit and calls `gui.popScreen()`. Right is free to mean "B" here specifically because strafing has no meaning while the game is frozen, mirroring how fire/back already borrow the badge's 4 physical buttons for different jobs depending on mode. The overlay intentionally shows just "Exit" with no on-screen button hint — precedent elsewhere in the GUI is to teach controls once via a screen's own convention rather than annotate every menu row.

## OLED header and a game-data footer

`VectortankScreen::render()` opens with `OLEDLayout::drawStatusHeader(d, "Grenada")` — the same clock/battery/wifi status bar every other screen draws itself (there's no automatic GUIManager-level chrome; see `OLEDLayout::drawStatusHeaderImpl()`). It was safe to add without touching the 3D scene because the header only occupies roughly the top 10 rows (`kHeaderRuleY`=8), well above the horizon (`kHorizonY`=32) and the mountain skyline's peak (~18px above the horizon at most).

The bottom of the screen got a matching game-data footer — FPS, a horizontal compass, and a live HP readout — but none of `OLEDLayout`'s three existing footer styles (`nav`, `action`, `star`, `game`) fit, since they're all built around a single text string plus an optional button-glyph chip, not three independent data columns. `drawVectortankFooter()` draws its own rule + columns directly in the same `OLEDLayout::kFooterTopY..kScreenH` band instead. Unlike the header, it has to blank that band first (`d.drawBox` in color 0) before drawing: the 3D scene's near geometry can reach all the way to the bottom row, so the footer would otherwise show scene edges bleeding through the text. FPS is a trailing 1-second moving average, not a smoothed instantaneous reading: `recordFrameAndGetFps()` keeps a `kFpsSampleCap`-entry (240) ring buffer of recent frame timestamps and counts how many fall within the last `kFpsWindowMs` (1000ms) — that count *is* the average fps over the window, computed fresh every frame without needing a decay constant. An earlier version used an exponential moving average (`gFpsSmoothed*0.9 + instFps*0.1`) instead; it was replaced because a smoothed instantaneous `1/dt` isn't actually a "1s moving average" despite reading like one. The compass reuses the same "bearing-locked" idea as the mountain skyline and radar: forward is always the fixed center pixel, and the N/E/S/W letters scroll past it as the camera turns, via a plain linear degrees-to-pixel mapping (`kCompassPxPerDeg`) rather than the mountain skyline's perspective projection — a compass ribbon has no depth to project. HP renders `gPlayerHealth` (see the splash-damage and solid-body-collision sections below for what drains it) as a plain `"HP <n>"` integer, no percent sign.

## Removing the radar's own player marker

The radar originally drew two brightened center pixels (`badgeMatrix.setPixel(3,3, ...)`/`(4,3, ...)`) marking the player's own position, drawn after the artifact mask so they'd never be masked by a coincident blip. On-device testing found this redundant — the player is always exactly at matrix-center by construction (the radar is bearing-locked to the camera), so a fixed marker there added nothing an empty center cell didn't already communicate — and the two pixels were removed from `drawRadar()`.

## LED-matrix flicker: the panel has no double-buffering, badge-wide

Testing the explosion-marker feature below surfaced that the *entire* radar picture visibly flickers every ~100ms redraw, not just the intended 1-second explosion blink. The cause has nothing to do with pixel brightness or any blink/auto-breath register — the IS31FL3731 driver this badge uses (`Adafruit_IS31FL3731`, wrapped by `LEDmatrix`) never uses the chip's two independent hardware frame buffers. Every `LEDmatrix::setPixel()` (and therefore `clear()`/`fill()`/`drawMask()`, which are all just loops of `setPixel()`) writes straight to whichever frame the chip is currently *displaying*, with no atomic buffer swap — the Adafruit driver exposes `setFrame()`/`displayFrame()` for exactly this, and `Adafruit_IS31FL3731::begin()` calls `displayFrame()` exactly once at init and never again. That's a property of the shared `LEDmatrix` wrapper, not something Vectortank introduced: no caller anywhere in the firmware (ambient `LEDAppRuntime` modes, the MicroPython matrix bridge, `SettingsScreen`'s brightness preview) ever calls `setFrame()`/`displayFrame()` either. It happened to go unnoticed elsewhere because `LEDmatrixAnimator::update()` only redraws when its mask/brightness actually changed (see its `maskChanged`/`brightnessChanged` guard), while the radar redraws unconditionally every ~100ms tick regardless of whether the picture moved — a git-history check turned up zero prior mention of frame buffering, tearing, or flicker anywhere in `LEDmatrix.cpp`'s commit history or this wiki, so this reads as an unexamined gap rather than a considered tradeoff.

`LEDmatrix` gained `beginFrameBatch()`/`endFrameBatch()` (`firmware/src/hardware/LEDmatrix.{h,cpp}`) to fix this badge-wide: `beginFrameBatch()` points the driver's write target (`driver_.setFrame()`) at whichever of the chip's two frames *isn't* currently displayed, so every `setPixel()`/`clear()`/`drawMask()` call in between lands there instead; `endFrameBatch()` flips the display register (`driver_.displayFrame()`) to that now-fully-drawn frame in one atomic step, then points the driver back at it so any subsequent *non-batched* single `setPixel()` call (a live one-pixel brightness preview, for instance) still writes straight to what's on-screen, unchanged from before. `LEDmatrix::init()` explicitly zeroes the second frame's PWM registers right after `driver_.begin()` so the hidden back buffer starts blank rather than whatever was left in chip memory at power-on. `drawRadar()` is the first (and so far only) caller: it wraps its `clear()`+`drawMask()`+explosion-marker `setPixel()` calls in one `beginFrameBatch()`/`endFrameBatch()` pair, so the panel only ever shows the finished radar picture, never an intermediate clear-then-repaint. The capability is now available to any other whole-panel-redraw caller, though none currently need it since they redraw conditionally rather than every tick.

## Explosion markers: a non-masking flash independent of the strobe

Every explosion (not just the close ones that trigger the full-panel strobe above) now marks its own world location on the radar, via `markExplosionForRadar()` pushing into a small fixed pool (`gExplosionMarkers[kMaxExplosionMarkers]`, 8 slots). `drawRadar()` draws each active marker's cell as an individual `setPixel()` call after `drawMask()` — deliberately never touching any other cell, so a flashing explosion can't mask a nearby artifact blip the way redrawing the whole mask a second time would.

Testing surfaced a bug in the first version: the marker's "off" phase simply skipped writing the cell (leaving whatever `drawMask()` had already painted there), so a marker landing on the same cell as an artifact blip never appeared to flash — the blip brightness just sat there the whole time, steady rather than blinking. The fix makes both phases explicit: on-phase writes `kExplosionMarkerBrightness` (255), off-phase writes `0`, unconditionally, for the marker's own cell only. The blip isn't actually lost by this — `drawMask()` repaints every alive artifact fresh from `gArtifacts` on every non-strobing tick, so the blip reappears the instant the marker's 1-second window (`kExplosionMarkerDurationMs`) ends and the marker deactivates.

## Opponents: billboard stick figures, not real 3D skeletons

Opponents (`struct Opponent`, `firmware/src/screens/VectortankScreen.cpp`) are drawn as flat, always-camera-facing "billboards" rather than real 3D geometry — a fixed local pose (head/spine/arms/legs) projected from one point (the figure's feet) and scaled by `kFovScale / depth`, the same perspective scale `project()` itself applies to a world-space vertical delta. That was a deliberate choice over a fully-3D skeleton: a billboard costs one `toCameraSpace()`/`project()` call per opponent (same as a particle) instead of the 8-to-14-vertex cost a rotating 3D skeleton would need, and sidesteps needing a convex-hull silhouette for a non-convex figure — occlusion is a single point test (`occludedByArtifact()`) against the figure's root, reusing the exact same test particles/projectiles already use. The tradeoff is that an opponent never visually turns to show a side profile; given the 128×64 1-bit display can't resolve fine joint detail past a few meters anyway (subtle motion is invisible at that resolution, only large limb swings read), the arcade "always-facing" convention (`Battlezone`'s own enemies did the same) was judged good enough.

Animation is entirely procedural — a walk-phase float (`o.walkPhase`) drives every joint angle via `sinf()`, the same trick `mountainHeightPx()` uses for the skyline — rather than authored keyframes or skinning, since neither exists anywhere in this firmware's toolchain. Each opponent's `walkPhase` is randomized at spawn (`makeOpponents()`) so a group of opponents doesn't step in visible lockstep. Death is a `deathK` scalar (1 = standing, 0 = collapsed) that shrinks every joint's height offset toward the fixed feet over `kOpponentDeathDurationS` (0.3s), reusing the same joint-offset math the walk cycle already computes rather than a separate collapse animation. The head is drawn as a small filled rounded box (`oled::drawRBox` with corner radius == half its side, since there's no dedicated circle primitive) rather than a bare line endpoint, sized in screen pixels from the same distance scale and clamped (`kOppHeadRadiusMinPx`/`MaxPx`) so it neither vanishes up close nor balloons at range.

Sizing went through two on-device passes: full scale read as too large next to the artifacts, halving it went too far the other way, and 75% (`kOppHeadY` etc., all scaled from the original ~1.8-world-unit-tall proportions) is what shipped. Halving the visual size also caused an unrelated bug: the projectile hit-test's vertical bound had been tied to the same visual-height constant, and once that fell below `kShotSpawnHeight` (1.0), a fired shot was almost always *above* the hittable band for its entire arc, making opponents read as indestructible. The fix decouples them — `kOpponentHitHeight` (2.0, comfortably covering the shot's full ~1.85-apex arc) is now independent of whatever `kOppHeadY` etc. draw on screen, so resizing the figure never again silently breaks whether it can be hit.

## Splash damage: every explosion, not just a direct hit

All three explosion sites in `stepProjectiles()` (ground miss, artifact hit, opponent hit) now call `applySplashDamage()`, which damages the player and every living opponent within `kSplashRadius` (3 world units) of the blast, falling off linearly from `kSplashMaxDamage` (20) at the center to 0 at the edge. This stacks on top of a direct hit's own fixed damage (`kOpponentShotDamage`) rather than replacing it — a directly-hit opponent is almost always inside its own explosion's radius too, so a precise shot still deals more total damage than a near-miss, which is the point of keeping both systems rather than folding direct hits into splash entirely. Standing too close to your own shot when it lands now costs the player health as well, via the same function.

## Durable obstacles and solid-body collision

Artifacts no longer die to a direct hit: `stepProjectiles()`'s artifact-hit branch still triggers the full explosion/splash/strobe/radar-marker sequence at the box's surface (the hit-test itself — footprint inside `a.half`, height under `a.height` — is unchanged, since a shot was already colliding against the box as a solid volume, not a destructible one), but no longer sets `a.alive = false`. That turns every artifact into a permanent piece of level geometry rather than something to clear out.

Making them *look* solid meant also making them *act* solid: `resolveArtifactCollision()` runs after the player's movement (`gCam.move()`/`strafe()`) and after each opponent's walk-toward-camera step, pushing the mover's position back outside any artifact's bounding box (expanded by the mover's own collision radius — `kPlayerCollisionRadius`/`kOpponentCollisionRadius`, both 0.4) it ends up inside, along whichever of the box's 4 sides was penetrated least. This is a post-move position correction, not a pre-move velocity clip — cheap (one bounds check per artifact, only doing the 4-side penetration math for boxes actually overlapping) and adequate at this game's movement speeds, though it doesn't handle a mover tunneling past a box's center in a single frame, which neither the player's nor an opponent's per-frame movement distance is fast enough to do against the artifacts' typical half-widths (0.8-1.8) in practice.

## Bigger, streaking explosions

The original explosion burst (14 particles, 1.8-3.5 world-units/s, 0.25-0.55s lifetime) read as a small dust puff once opponents and their combat were in place — `kExplosionParticleCount`/`kExplosionSpeedMin`/`Max`/`kExplosionLifetimeMin`/`Max` were bumped to 26 particles at 2.5-5.5 units/s living up to 0.8s (`kMaxParticles` grew from 64 to 96 to give the bigger, longer-lived bursts enough pool headroom for several to overlap). The bigger visual change is how each particle draws: `Particle` gained `px`/`py`/`pz` (the previous frame's position, saved at the top of `stepParticle()` before integrating), and `drawScene()`'s particle loop now projects both the previous and current position and draws a `drawLine()` streak between them instead of a single `drawPixel()` dot — the same projection math, just drawn as a short segment. At this particle count and speed, individual dots per frame read as a static-looking cloud; a streak per particle reads as motion, which is what makes the burst look like an explosion rather than scattered debris.

## The minimap no longer shows artifacts

`drawRadar()` used to build its 8x8 mask from both alive artifacts and (later) opponents. Now that artifacts are durable, permanent level geometry rather than something to track and clear (see the durable-obstacles section above), showing every one of them on an 8x8 grid was just static clutter the player couldn't act on — the mask-building loop over `artifacts[]` was removed, leaving the radar to show only opponents (now brighter, moving blips) and explosion markers. `artifacts`/`artifactCount` stay in `drawRadar()`'s signature (marked `(void)`-unused) rather than being dropped, so a future feature — e.g. surfacing only a nearby obstacle — doesn't need a signature change to add them back.

## Pause menu becomes a real menu: Resume, New Game, and a permanent game-over variant

The pause overlay's single "Exit" row grew into a real three-item menu (`kPauseMenuItemCount = 3`: Resume, New Game, Exit — `kPauseItemResume`/`kPauseItemNewGame`/`kPauseItemExit`), navigated with a cursor (`VectortankScreen::pauseCursor_`) instead of one button doing everything. Left (raw edge, "x") cycles the cursor forward through `nextPauseItem()`; the stick's Y axis does the same navigation (up = previous, down = next), latched via `VectortankScreen::pauseStickDir_` so a held tilt past the `kStickHi` (0.5) threshold doesn't repeat-fire every frame — it only re-arms once the stick crosses back under `kStickLo` (0.2). Right/B confirms the highlighted row: Resume unpauses, New Game calls `resetGame()`, Exit calls `gui.popScreen()`. This replaced an earlier design where the raw `downPressed` edge closed the menu directly as an instant "resume" shortcut (mirroring the "B" confirm/"A" cancel semantic pairing, since down is `cancel`'s physical button) — once the stick took over down/up for cursor navigation, that shortcut had nowhere left to live, so Resume became an explicit menu row instead. `nextPauseItem()` skips `kPauseItemResume` whenever `gameOver_` is set, since there's no "resume" from 0 HP; the cursor defaults to Resume every time the menu opens (`onEnter()` and the back-press branch of `handleInput()` both set `pauseCursor_ = kPauseItemResume`), except the game-over transition, which defaults to New Game instead since Resume isn't offered there.

`gameOver_` (`VectortankScreen.h`) is a permanent variant of `paused_` set the instant `gPlayerHealth` reaches 0 in `handleInput()`, reusing the exact same overlay (`drawPauseMenu()` takes a `gameOver` bool that swaps the title between "PAUSED" and "GAME OVER") rather than a separate screen — the frozen-scene-behind-an-overlay presentation already fit a "run ended, here's what's next" moment without new chrome. The only way out is New Game (which calls the same `resetGame()` the pause menu's New Game item and `onEnter()` both use) or Exit (`gui.popScreen()`).

`resetGame()` is a small refactor extracted from what `onEnter()` used to do inline: reseed the RNG, respawn artifacts/opponents, clear particles/projectiles, and reset health/kills/spawn-timer — now a single free function both `onEnter()` and the pause menu's New Game action call, so starting a fresh run mid-session doesn't need its own hand-maintained copy of the reset logic. Screen-owned members (`lastFireMs_`, `paused_`, `gameOver_`) are reset separately at each call site, since `resetGame()` only touches the module-level game-world globals. `seedRng()` was originally called with a fixed `1` — deliberately reproducible, matching the fixed `random.seed(1)` the `vt_engine.py` benchmark sweep used (see the MicroPython-comparison section above) — but every New Game and every fresh `onEnter()` therefore spawned the exact same artifact/opponent layout. `resetGame()` now seeds from `millis()` instead, so each run's layout differs; the benchmark-reproducibility property that motivated the fixed seed no longer applies once this is a shipped game rather than a Python-vs-C++ comparison harness.

## Kill count and a single anonymous high score

Every opponent death — direct hit or splash, doesn't matter which — increments `gKillCount` exactly once, at the single point `stepOpponents()` transitions `o.alive` to `false` once its death animation finishes (`o.deathT >= kOpponentDeathDurationS`). That's the one source of truth for kills regardless of how the opponent died, rather than incrementing at each damage-application call site. Immediately after, `saveHighScoreIfBetter()` compares against `gHighScore` and persists a new best live during play (not just at game-over), in its own NVS namespace (`"vectortank"`, key `"highscore"` — both well under the 15-character NVS key limit noted in `AssetRegistry.cpp`) via a local `Preferences` instance opened and closed per call, the same open/close-per-call convention every other `Preferences` user in this firmware follows (no shared global instance). There's no identity attached — it's a single scalar, not a leaderboard — matching what was asked for. `gHighScore` is loaded once per `onEnter()` via `loadHighScore()`; `drawPauseMenu()` shows the current run's `gKillCount` right-aligned against the "PAUSED"/"GAME OVER" title on the overlay's first row and `gHighScore` right-aligned against a "HIGH SCORE" label on the second, replacing an earlier compact `K:<n> B:<n>` single-line format.

## Escalating opponent spawns

`kActiveOpponentCount` (the initial wave `resetGame()` spawns) dropped from 5 to 4 for an easier start, now that `stepSpawner()` tops the opponent pool up over time: a timer (`gSpawnTimerS`) counts down each frame, and on expiry calls `spawnOneOpponent()` and resets itself to an interval that shrinks with `gKillCount` — `kSpawnBaseIntervalS` (8s) minus `kSpawnIntervalStepPerKillS` (0.25s) per kill, floored at `kSpawnMinIntervalS` (2s) so a long run gets harder but never turns into an unplayable firehose. `kMaxOpponents` grew from 6 to 14 to give the escalating spawner real headroom beyond the initial wave. `spawnOneOpponent()` deliberately reuses `makeOpponents()`'s existing ring-spawn/init logic for a single slot (calling it with count=1 into a throwaway one-element array) rather than duplicating the spawn-position math — it looks for a dead slot within the currently-active range first, and only grows `gOpponentCount` into unused pool capacity if every active opponent is currently alive.
