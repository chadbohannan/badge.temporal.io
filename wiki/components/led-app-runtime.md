# LEDAppRuntime: Ambient LED Ownership

`firmware/src/led/LEDAppRuntime.{h,cpp}` is the single long-lived owner of the badge's ambient LED matrix. Centralizing ownership in one runtime — rather than letting whichever screen or app is active drive the matrix directly — is what makes it possible for a foreground surface (the on-screen keyboard, a MicroPython app) to temporarily take over the LEDs and then hand them back to exactly the ambient pattern that was showing before, instead of leaving the matrix in whatever state the interrupting surface last drew.

It persists the selected LED mode, renders poster frames used for OLED previews of each mode, and implements the native animations and pattern generators directly — including a Game of Life mode and custom user patterns — so those run even when no MicroPython app is active. `Mode` covers ten states (`Temporal`, `Replay`, `Sparkle`, `Rain`, `Wave`, `Life`, `LifeRandom`, `Custom`, `Off`, `PythonApp`); `LEDScreen`'s carousel/editor calls `beginPreview()`/`updatePreview()`/`endPreview()` while a user is browsing modes, and only `commitMode()`/`commitLife()`/`commitCustom()` actually persists a choice — this preview/commit split is what lets the carousel show a live rendering of a mode without every scroll step overwriting the saved NVS state.

The Game of Life mode tracks the previous two generations (`lifePrev_`, `lifePrev2_`) specifically to detect still-lifes and two-cycle oscillators: `kStaleGrace` (8) ticks of no visible change trigger an automatic reseed rather than leaving the matrix frozen on a dead board. `PythonApp` mode is the ambient-runtime half of a folder app's `matrix.py` convention (see [badge app authoring](badge-apps.md)'s `AppRegistry::DynamicApp::hasMatrixApp`): `commitMatrixApp(slug)` records the chosen app and sets a pending-exec flag that `MicroPythonMatrixService` drains on its next service pass to actually source the registration script, rather than `LEDAppRuntime` executing Python directly.

## The override contract

Anything that wants to draw to the LED matrix in the foreground — including MicroPython apps via the [MicroPython bridge](micropython-bridge.md) — must bracket its drawing with `led_override_begin()` / `led_override_end()`, or use `matrix_app_start()` for the ambient-LED-matrix Python API surface (`matrix_app_*`, defined in the usermod at `firmware/micropython/usermods/temporalbadge/`). This is a contract enforced by convention, not by the type system: skipping the override calls and writing to the matrix directly would leave `LEDAppRuntime`'s saved state out of sync with the physical display, so the restore-on-exit behavior would show the wrong pattern the next time the ambient runtime regains control.

`firmware/src/screens/LEDScreen.cpp` owns the OLED-side carousel and editor UI for browsing and picking LED modes, but it goes through `LEDAppRuntime` rather than duplicating any pattern logic itself — per `firmware/src/README.md`'s "how do I" guidance, changing ambient LED behavior means editing `LEDAppRuntime`, not `LEDScreen`. `LEDAppRuntime` is itself an `IService` on the [cooperative scheduler](scheduler.md), which is how it keeps rendering ambient animations on every `loop()` pass independent of whatever screen or MicroPython app is currently in the foreground.
