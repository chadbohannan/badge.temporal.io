# LEDAppRuntime: Ambient LED Ownership

`firmware/src/led/LEDAppRuntime.{h,cpp}` is the single long-lived owner of the badge's ambient LED matrix. Centralizing ownership in one runtime — rather than letting whichever screen or app is active drive the matrix directly — is what makes it possible for a foreground surface (the on-screen keyboard, a MicroPython app) to temporarily take over the LEDs and then hand them back to exactly the ambient pattern that was showing before, instead of leaving the matrix in whatever state the interrupting surface last drew.

It persists the selected LED mode, renders poster frames used for OLED previews of each mode, and implements the native animations and pattern generators directly — including a Game of Life mode and custom user patterns — so those run even when no MicroPython app is active. `Mode` covers ten states (`Temporal`, `Replay`, `Sparkle`, `Rain`, `Wave`, `Life`, `LifeRandom`, `Custom`, `Off`, `PythonApp`); `LEDScreen`'s carousel/editor calls `beginPreview()`/`updatePreview()`/`endPreview()` while a user is browsing modes, and only `commitMode()`/`commitLife()`/`commitCustom()` actually persists a choice — this preview/commit split is what lets the carousel show a live rendering of a mode without every scroll step overwriting the saved NVS state.

The Game of Life mode tracks the previous two generations (`lifePrev_`, `lifePrev2_`) specifically to detect still-lifes and two-cycle oscillators: `kStaleGrace` (8) ticks of no visible change trigger an automatic reseed rather than leaving the matrix frozen on a dead board. `PythonApp` mode is the ambient-runtime half of a folder app's `matrix.py` convention (see [badge app authoring](badge-apps.md)'s `AppRegistry::DynamicApp::hasMatrixApp`): `commitMatrixApp(slug)` records the chosen app and sets a pending-exec flag that `MicroPythonMatrixService` drains on its next service pass to actually source the registration script, rather than `LEDAppRuntime` executing Python directly.

## The override contract

Anything that wants to draw to the LED matrix in the foreground — including MicroPython apps via the [MicroPython bridge](micropython-bridge.md) — must bracket its drawing with `led_override_begin()` / `led_override_end()`, or use `matrix_app_start()` for the ambient-LED-matrix Python API surface (`matrix_app_*`, defined in the usermod at `firmware/micropython/usermods/temporalbadge/`). This is a contract enforced by convention, not by the type system: skipping the override calls and writing to the matrix directly would leave `LEDAppRuntime`'s saved state out of sync with the physical display, so the restore-on-exit behavior would show the wrong pattern the next time the ambient runtime regains control.

`firmware/src/screens/LEDScreen.cpp` owns the OLED-side carousel and editor UI for browsing and picking LED modes, but it goes through `LEDAppRuntime` rather than duplicating any pattern logic itself — per `firmware/src/README.md`'s "how do I" guidance, changing ambient LED behavior means editing `LEDAppRuntime`, not `LEDScreen`. `LEDAppRuntime` is itself an `IService` on the [cooperative scheduler](scheduler.md), which is how it keeps rendering ambient animations on every `loop()` pass independent of whatever screen or MicroPython app is currently in the foreground.

## User-editable Replay text and font

Implemented 2026-09-28 on the `matrix_rework` branch, scoped 2026-09-23. `Mode::Replay` no longer scrolls a fixed bitmap; it scrolls a column buffer rasterized at runtime from a user-supplied string and a user-chosen font, through the same `frameFromColumns()` window mechanic (`LEDAppRuntime.cpp`) that always drove the scroll.

Rasterization reuses the OLED's `u8g2` font engine rather than a matrix-specific renderer: `LEDAppRuntime::rebuildReplayColumns()` sets `extern oled badgeDisplay`'s font, draws the string with `drawStr()`, and reads the glyphs back column-by-column with `getPixel()` into `replayColumns_` — `sendBuffer()` is never called, so nothing reaches the physical panel. Because `getPixel`/`drawStr` operate on the OLED's real 128-wide buffer, strings wider than 128px are rendered in successive `drawStr(-sliceStart, baselineY, text)` slices and stitched together. `replayColumns_` is capped at `kReplayColumnCap` (224 bytes, 8-byte pad on each side) and text at `kReplayTextCap` (24 chars + NUL); `ensureReplayColumns()` caches against the last-built text/font pair so unchanged calls (most ticks) are a no-op. This added a new coupling: `LEDAppRuntime` previously depended only on `LEDmatrix`, and now also depends on the OLED singleton purely to borrow its font rasterizer.

The font shortlist is fixed at five entries confirmed to fit the matrix's 8-row height (see `LEDAppRuntime::ReplayFont` and the `kReplayFontTable` in `LEDAppRuntime.cpp`, deliberately named to avoid colliding with the unrelated `ReplayFont`/`kReplayFontCount` globals in `firmware/src/ui/FontCatalog.h`): `spleen5x8` (default), `5x8`, `5x7`, `4x6`, `u8glib4`. Each is persisted by string id, not index, so reordering the shortlist later can't silently repoint an old save at the wrong font.

`LEDAppRuntime::posterFrame()` was de-staticized to take `state_` access, so the carousel's OLED thumbnail for Replay renders the user's actual committed text via `ensureReplayColumns(state_.replayText, state_.replayFont)` rather than a generic placeholder; this also dropped the `lifeSeed`/`custom` parameters other poster cases used to be passed explicitly, since posterFrame now reads `state_` directly for those too. Live editing goes through a new `previewReplay(text, font)` entry point, parallel to `updatePreview()`'s role for the Life/Custom byte-array drafts — `LEDAppRuntime::effectiveReplay()` resolves whether `buildFrame()` should use the in-progress preview draft or the committed state.

In `LEDScreen.cpp`, Y on the carousel's Replay slot (footer label "text") goes straight to `TextInputScreen`, the way `BadgeInfoViewScreen::onItemSelect` does. "send" calls `commitReplay()` with the committed font and returns to the carousel on the Replay slot (the preview is restarted, since `commitReplay()` re-applies the ambient state); cancelling the keyboard changes nothing. An earlier design had an intermediate "Replay Text" view with a font-cycling key and a live preview; it was removed, so the font shortlist has no UI today and the font stays whatever was last saved (default `spleen5x8`). Persistence extends the existing `loadState()`/`saveState()` `/led_state.json` round-trip with `replay_text` and `replay_font` fields; the JSON doc and file-read cap grew from 384/512 to 768 bytes to fit them.

Default state is `replayText = "REPLAY"`, `replayFont = spleen5x8` — a generated approximation, not the old hand-authored wordmark bitmap (which was deleted). This is a deliberate visual change for every badge that had `Mode::Replay` selected before this shipped: confirmed with the user rather than assumed.

The carousel's first footer label is "rate": stick up raises and stick down lowers the frame rate in whole frames per second (1 to 60) and X switches the stick to brightness, which is no longer named in the footer but still works and still shows as a `brt` line. `LEDScreen` converts between fps and the frame period in ms that `LEDAppRuntime` and `/led_state.json` keep, so saved states are unchanged and an older period such as 120 ms shows as its rounded rate (8 fps) until it is adjusted. `LEDAppRuntime::kDefaultDelay` is now 100 ms (10 fps), for fresh states only.

The [host harness](../systems/host-test-harness.md) `replay-text` script drives this flow end to end (Y opens the keyboard, edit, send returns to the carousel, which still browses) against goldens. Saving through it exposed a use-after-free in `loadState()`: the file buffer was freed before ArduinoJson read the strings that pointed into it. That is fixed, along with [two more sites with the same pattern](../syntheses/known-cruft-and-dead-code.md).
