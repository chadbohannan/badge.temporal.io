# OTA and Asset Registry

`firmware/src/ota/` implements two related but distinct download systems: `BadgeOTA` (whole-firmware updates from GitHub Releases) and `AssetRegistry` (a generic, registry-driven fetcher for everything else — the Doom WAD, sound packs, fonts, and Community App bundles). Both are wired into the main loop through `OTAService`, an `IService` on the [cooperative scheduler](scheduler.md) that staggers the two on every WiFi-up edge specifically so their TLS handshakes don't overlap — see [internal-DRAM contention](../concepts/internal-dram-contention.md) for why that matters.

## Firmware OTA

`BadgeOTA` polls `REPO_RELEASES_API_URL` (GitHub's releases API) once a day, caching the latest tag and matching `firmware.bin` asset URL in NVS (`badge_ota` namespace). It's asymmetric by design: `checkNow()` holds the global TLS gate for the entire handshake and must only be called from task context (never Core 1's main loop), while `beginCheckAsync()` spawns a Core 0 worker so the GUI, input, and IR pump never freeze waiting on a GitHub round-trip. The installed binary is layout-agnostic — it uses `esp_partition_find_*` for every data partition rather than hardcoded flash offsets — so the same `firmware.bin` release asset boots correctly on both partition tables described on the [badge device](badge-device.md) page, as long as the build stays under the smaller `_doom` layout's 3.84 MB `app0` slot. A first-boot rollback safety net (`markCurrentAppValidIfPending()`, called once the GUI has run healthily for ~30 s) lets the ESP32-S3 bootloader auto-revert to the previous OTA slot if a fresh install never reaches that point.

### In-place partition layout migration

Beyond the two build-time partition tables ([badge device](badge-device.md) documents `replay2026` vs. `replay2026-expanded`), `BadgeOTA` also contains an *in-place* migration path (`migrateToExpandedLayout()`) that rewrites the partition-table sector at flash offset `0x8000` with an embedded `_ver2` blob and reboots — no full reflash required, because both layouts keep `app0` at the same offset. This is compile-time disabled in public builds (`BADGE_ENABLE_IN_PLACE_LAYOUT_MIGRATION` is off), which forces anyone who wants the larger layout today to run `firmware/scripts/erase_and_flash_expanded.sh` over USB instead; the in-place code path is kept in the tree for future hardware qualification rather than deleted. The failure surface is narrow but real — a power cut during the roughly 200 ms erase+write window can brick the partition table, so the UI is expected to show a recovery QR *before* asking for migration confirmation, and an `RTC_NOINIT_ATTR` magic value (cross-checked against `esp_reset_reason() == ESP_RST_SW` to rule out unrelated RTC artifacts) distinguishes "we just completed a confirmed in-place migration" from an ordinary reflash to a different layout for the post-boot UI.

## AssetRegistry: the generic install-on-demand mechanism

`AssetRegistry`'s `registry.json` (schema v2) is the same download mechanism that backs [Community Apps](community-apps-registry.md) — the setting that points to it, `community_apps_url`, is the current name for what the header comments still call `asset_registry_url` internally, kept as a transparently-read legacy alias so old `settings.txt` files keep working. A registry entry is one of two kinds: `"file"` (a single asset like `doom1.wad`, with an optional `sha256` corruption check) or `"app"` (a multi-file bundle installed under a `dest_dir`, with per-file URLs and hashes inlined in the manifest rather than requiring a second manifest fetch per app). Installed-version state per asset lives in NVS under `badge_assets`, keyed by asset id; installs stream into a `.tmp` path and atomically rename over the live file or directory, so a failed or interrupted install never corrupts a previously-good copy. `registry::installAll()` walks every registered asset and installs whichever ones are `kNotInstalled` or `kUpdateAvailable`, which is what the [`AssetLibraryScreen`'s](gui-screen-stack.md) synthetic "Download all" row calls rather than looping over `install()` per entry itself; that screen also caches each row's `AssetStatus` (`[*]`/`[+]`/`[!]`/`[ ]` bracket markers) once per refresh instead of calling `statusOf()` on every render frame, since NVS reads on every one of up to 60 fps redraws would be wasteful for state that only changes on install/remove/refresh.

## Storage introspection for the "Expand storage" prompt

`BadgeOTA` also exposes `ffatPartitionBytes()` vs. `ffatVolumeBytes()` specifically so the Firmware Update screen can detect the case where an OTA firmware update shipped a wider `ffat` partition table than the currently-*formatted* FAT volume is using, and offer a one-tap "Expand storage" reformat rather than leaving the extra space silently unreachable until a full factory reflash.
