# Ignition Flash Workflow

`ignition/flash_worker/workflows.py` and `activities.py` are the concrete Temporal implementation behind the narrative on the [Ignition system page](../systems/ignition.md). Four workflow types, all registered on the `badge-flash` task queue: `BuildFirmwareWorkflow` (one `build_firmware` activity call, delegating to `firmware/build.sh -n` rather than reimplementing PlatformIO invocation so Ignition and a direct build can never drift apart), `DetectBadgesWorkflow` (the `--expected-count` preflight described on the system page), `BadgeFlashWorkflow` (one durable per-badge state machine), and `FlashBadgesWorkflow` (the fan-out parent).

## Why retries are hand-rolled instead of just a RetryPolicy

Every activity in `BadgeFlashWorkflow` uses a `maximum_attempts=1` retry policy (`_ACTIVITY_ONCE`) even though the workflow clearly does retry flashing up to three times and boot verification up to two. The reason is that a naive Temporal-level retry would just re-run the same activity — but a failed flash often means the badge dropped off USB and re-enumerated on a different port, so simply re-running `flash_badge_images` against the *old* port would fail identically. The workflow instead loops manually: each attempt starts with `resolve_badge_port` (using the resolved `usb_id`, or falling back to the original port, or falling back to matching on the macOS USB-serial "family" of the original port when even the port number changed) before ever calling flash or verify, so a genuine re-plug or re-enumeration is transparently absorbed between attempts rather than producing a hard failure. Flash attempts back off `5 * attempt` seconds between tries; boot-marker verification attempts (2 max) back off a flat 3 seconds; clock sync only runs once, and only after boot verification has already succeeded.

## USB bootloader recovery is a special case, not the normal path

`prepare_badge_devices_for_flashing` detects connected badges and then calls `_recover_usb_bootloader_ports`, but that recovery step is scoped narrowly: `_needs_usb_bootloader_recovery(port)` only matches ports whose serial device name fits a specific "QA firmware" pattern (`_QA_USBMODEM_RE`) — a badge running the current native-USB-JTAG firmware doesn't need this at all, since esptool's own auto-reset handles it. For the ports that do match, `_pulse_bootloader_control_lines` opens the port directly with `pyserial`, drives `DTR=False, RTS=True` (asserting boot-mode), holds it, then flips both back and releases DTR — the same RTS/DTR reset trick a USB-JTAG bootloader normally handles in hardware, done manually here for a badge whose current firmware doesn't expose that pin sequence itself. Up to `USB_BOOTLOADER_RECOVERY_CONCURRENCY` ports are pulsed in parallel via an `asyncio.Semaphore`, and success is judged by the port actually disappearing (the device re-enumerating under bootloader mode) rather than by any acknowledgement over the wire.

## Verification runs as isolated subprocess probes, not inline asyncio

`verify_badge_boot_marker` and `sync_badge_clock` don't read the serial port directly inside the activity's own asyncio event loop — each spawns a short, self-contained Python script as a subprocess (via `textwrap.dedent`-embedded source passed to `python -c`) that opens the port itself, polls `readline()` against a regex for success (`Temporal Replay 2026\s+-\s+` for boot) or failure (`Guru Meditation`, `Backtrace:`, `stack canary`, `Brownout detector`, etc.) patterns, and exits with a distinct code per outcome (0 success, 2 detected crash, 1 timeout). Isolating this in a subprocess means a serial read that hangs or a crash in the probe script can't take down the worker's own event loop or block other concurrent per-badge activities sharing it.

## BLE verification exists but is never actually invoked

`verify_badge_ble` is a fully implemented activity — registered with the worker, watching for `[badgebeacon] broadcasting`, `[map/ble]`, or `[ble] scan started` log lines and failing fast on BLE-specific crash signatures (`ESP_ERR_NO_MEM`, `BLE_INIT: Malloc failed`, specific `reset_reason` codes). But `BadgeFlashWorkflow.run()` never calls it: the workflow hardcodes a synthetic `ble_verify` result (`"success": True, ... "[verify] BLE verification skipped."`) instead of awaiting the real activity. This lines up exactly with [BLE room presence](ble-proximity.md) being excluded from the public `replay2026` build at the source-filter level — a badge built from this public repo will never emit any of `verify_badge_ble`'s success patterns, so calling it for real would just make every public flash fail on a feature the firmware was never built to have. The activity and its wiring were evidently written against a build variant (internal or historical) that still compiled `ble/` in, and the public workflow was adjusted to skip it rather than delete it.
