# Data Bundle: Schedule, Speakers, Floors

The badge's schedule, speaker, and floor-map screens don't fetch data over the network — the content is generated once at build time and embedded directly into the firmware binary. `data/in/schedule.yaml`, `data/in/speakers.md`, and `data/in/floors.md` are the hand-edited, human-readable sources; `data/build-data.py` (requiring `msgpack` and `pyyaml`) compiles them into `data/out/schedule.json`, `speakers.json`, `floors.json`, a generated `data_api.h`, and `data/out/bundle.bin`.

`bundle.bin` is what actually reaches the firmware: it's linked in via `board_build.embed_files` in the `replay2026` PlatformIO environment (see the [firmware system page](../systems/replay2026-firmware.md) for why that line has to be redeclared per-environment rather than inherited), and consumed at runtime by `firmware/src/api/DataCache.cpp`, `firmware/src/screens/ScheduleData.cpp`, and `firmware/src/screens/MapScreens.cpp` via the linker-provided `_binary_bundle_bin_start`/`_binary_bundle_bin_end` symbols.

`DataCache` resolves content through a three-step fallback chain, preferring the freshest source but never leaving the screen with nothing to render: it first tries `/data.bin` on FATFS (validated by a `'TBDS'` magic, a version field, and a CRC32 covering everything from the total-size field onward), falls back to a caller-supplied download function that can atomically replace `/data.bin` when FATFS is missing or corrupt, and only falls back to the embedded `bundle.bin` copy linked into the firmware binary as a last resort. In the current public build `defaultDownloader()` is a stub that always reports unavailable (the firmware "no longer reaches out to the Replay API," per its own comment) — so in practice, without a custom downloader wired in, the effective chain is FATFS-if-present-and-valid, else embedded. `statusLabel()` exposes a 3-character on-screen code (`EMB`/`CCH`/`NEW`/`SYN`/`ERR`) combining the active source with the last refresh outcome, useful for diagnosing which of the three sources actually served a given schedule/map screen. The [Schedule Screen](schedule-screen.md) shows the same pattern independently at its own layer: `ScheduleData.cpp` reads two hardcoded FATFS cache paths before falling back to this embedded bundle, and — like `defaultDownloader()` — nothing in the public tree ever writes those cache paths, so the schedule is effectively always the embedded, build-time content on a badge built from this repo alone.

Unlike most generated output in this repo (compare `firmware/data/`, which is gitignored and rebuilt locally), `data/out/` is committed: the README notes it should stay generated *and* checked in because the public release flow consumes it directly, so a firmware build doesn't require running the data pipeline first unless the schedule content itself changed. Updating schedule, speaker, or floor content means editing the `data/in/` sources and re-running `python3 build-data.py` from `data/`, then committing the regenerated `data/out/` files alongside the source edit.

## Source format

`data/in/speakers.md` is a single Markdown table (`Name | Company | Title | Description`) — one row per speaker, description column often left blank. `data/in/schedule.yaml` is the day/event list `build-data.py` cross-references against both speaker names and floor locations, warning (not failing) on any event that names a speaker or location it can't resolve. `data/in/floors.md` is a sequence of `#`-headed floor sections (e.g. "Level 00", "Concourse", "Mezzanine"), each with a one-line italic subtitle and a numbered list of points of interest; a point can carry inline backtick-tagged metadata — `` `icon: temporal` `` selects a map icon, parsed by `build-data.py`'s `_SECTION_RE` into the structured `floors.json`. The floor list ends with an "Off-Site" section using code prefix `9`, which is how off-venue locations (a 5K run start point, in the current data) are distinguished from in-building floors in the generated map data without a separate schema; whole-floor references (as opposed to a specific section) use `floor_idx*100 + 99` as their loc code, one more fact [BLE room presence](ble-proximity.md)'s decode logic mirrors exactly.

**A tag that's parsed but discarded:** `floors.md` entries can also carry `` `sponsors: augment-code, technoidentity` `` tags (see the Concourse section's sponsor booths), and `_SECTION_RE`'s trailing `(?:\s*\`[^\`]+\`)*` group matches them so the regex doesn't fail on the extra inline code — but nothing ever captures that group into a named field, and `clean_floors()`'s output dict only ever contains `idx`/`loc`/`title`/`alias`/`icon`/`desc`. The sponsor slugs are present in the human-authored source and visually meaningful to someone reading `floors.md`, but they never reach `floors.json` or the firmware. Whether that's intentional (the booth's free-text `desc`, e.g. "Augment Code booth.", already carries the same information for display purposes) or an unfinished feature isn't clear from the source alone — worth confirming with whoever authors the floor data before assuming either way.
