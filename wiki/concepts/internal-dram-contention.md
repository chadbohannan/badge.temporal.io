# Internal-DRAM Contention

The ESP32-S3 module on the badge has plenty of *total* RAM (8 MB PSRAM plus roughly 250 KB internal DRAM — see the [badge device](../components/badge-device.md) page), but several subsystems each need a large *contiguous internal* allocation at the same moments, and internal DRAM is the scarce, fragmentable resource that actually causes failures. This concept threads through several otherwise-unrelated files, and none of the individual component pages state the underlying constraint on their own:

- **TLS handshakes** (`firmware/src/api/TlsGate.h`) pull 16-32 KB of contiguous internal-DRAM working buffers plus 4-16 KB of session state, and `WiFiClientSecure`/`NetworkClientSecure` add another ~10 KB on top. Two concurrent TLS sessions — say, the [OTA check](../components/ota-and-assets.md) handing off to a Community Apps registry refresh — reliably tripped `mbedTLS -32512 SSL - Memory allocation failed` before this was addressed. The fix is `badge::TlsSession`, a single process-wide **recursive** FreeRTOS mutex that every `WiFiClientSecure` open-site must acquire first (recursive so a defensive nested HTTPS-from-callback pattern can't deadlock, even though nothing does that today). A companion predicate, `tlsHeapHeadroomOk()` (40 KB free + 26 KB largest contiguous block — empirically the peak observed during a healthy handshake), gates entry independent of the mutex itself.
- **The BLE controller** (~30 KB) and the **WiFi LwIP stack** (~50 KB) can't coexist in the internal-DRAM budget at all — see [BLE room presence](../components/ble-proximity.md) — so bringing up BLE means tearing WiFi down first, and `BleBeaconScanner::blocksWiFi()` exists so `WiFiService` can check before attempting a reconnect while BLE holds the radio.
- **`btdm_controller_init`** empirically needs roughly a 32 KB contiguous free block to succeed, which ordinary MicroPython/LwIP/TLS allocation traffic can fragment away entirely — hence `BleBeaconScanner::reserveMemoryAnchor()`/`releaseMemoryAnchor()` pre-claiming a slab specifically to guarantee that block exists when BLE needs it, freed again the moment BLE init actually consumes it.
- **A fresh OTA firmware install** (`ota::prepareFirmwareInstallHeap()` in [OTA and assets](../components/ota-and-assets.md)) explicitly waits out any in-flight community-registry HTTPS fetch and forces a MicroPython GC pass before starting `Update.begin()`, for the same reason: less fragmentation, more contiguous headroom, right before the one operation (writing a new firmware image) that must not fail partway through.
- **`badge::kickIdleTaskWatchdog()`** is the same family of problem from a different angle: a task spinning through mbedTLS/crypto work without yielding can starve the per-CPU IDLE task long enough to trip ESP-IDF's task watchdog, so TLS/socket-heavy code paths deliberately park for ~15 ms before chunky work rather than relying on a bare `yield()`.

The common shape across all five: **a large contiguous internal-DRAM (or CPU-time) claim, a scarce shared resource, and a purpose-built serialization or reservation mechanism** rather than a generic allocator fix, because none of PSRAM, a bigger heap, or a smarter allocator solves "I need this many contiguous bytes/cycles at exactly this moment, and something else on another core might want the same thing right now." Any new feature that opens its own `WiFiClientSecure`, brings up BLE, or does sustained crypto work should be checked against this list before assuming it can simply run alongside what's already active.
