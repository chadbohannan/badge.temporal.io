# Offline-First Runtime

The badge's firmware boots straight to its local UI: no QR pairing gate, no private Replay backend transport, and no background ping-polling loop. `firmware/src/README.md` calls this out explicitly as the "Offline Runtime" and notes that native ping-backed messaging code was removed for the offline public firmware — `firmware/src/messaging/` is reserved for a future local messaging surface rather than housing an active feature today. This isn't an oversight or a stripped-down demo build; it's what makes this public repository buildable and useful by anyone without also needing access to Temporal's private backend services, which `AGENTS.md` and this wiki's [CLAUDE.md](../CLAUDE.md) both call out of scope for this repo.

## What still needs a network, and what doesn't

Contact exchange (the [Boops](../components/badge-boops.md) system) is entirely local over IR and writes to `/boops.json`; a badge's own editable contact card lives in NVS and can be changed from the Badge Info screen or over USB serial with `badge.contact()` / `badge.set_contact({...})` — no network round-trip either way. The schedule, map, and visual content are similarly self-contained: they come from the [embedded data bundle](../components/data-bundle.md) compiled into the firmware at build time, not fetched live.

What *does* need WiFi is explicitly the optional layer: GitHub-backed OTA updates and the generic asset fetcher (see [OTA and assets](../components/ota-and-assets.md)), the [Community Apps](../components/community-apps-registry.md) install flow, and whatever a MicroPython app deliberately does with the explicit `badge.http_get`/`badge.http_post` hacker API. A fully-implemented BLE venue room-presence feature (see [BLE room presence](../components/ble-proximity.md)) goes a step further than any of those: it's excluded from the public build entirely at the source-filter level rather than merely being optional at runtime, presumably because it depends on venue-side beacon infrastructure this repo has no other trace of. `screens/MapScreens.cpp` is the model for handling that exclusion cleanly — every BLE call is wrapped in `#ifdef BADGE_ENABLE_BLE_PROXIMITY`, so the Map screen simply runs without proximity-based floor highlighting in the public build rather than failing to link.

Not every remnant of the pre-offline design was excluded that cleanly, though: the [screen stack](../components/gui-screen-stack.md)'s `ScreenAccess`/`badgeState` routing (`kPairedOnly`/`kAny`/`kUnpairedOnly`, checked on every screen transition) is live, compiled code from what was evidently once a real pairing gate, but every branch that could have blocked a screen today just returns `true` — the mechanism runs on every navigation and does nothing. It's a good example of the difference between a feature *excluded* from the public build (BLE) and a feature *retired in place*, still executing, just inert. That API is intentionally request-triggered rather than a background polling service — `firmware/src/README.md`'s guidance for adding HTTP behavior is explicit that it belongs in `micropython/badge_mp_api/mp_api_http.cpp` or app code, "do not add background badge-owned API polling." Keeping the always-on badge experience network-independent, and making every network-touching feature something a user or app explicitly triggers, is the throughline connecting the offline runtime, the storage model's NVS-survives-everything guarantee, and the public/private scope boundary in `AGENTS.md`.
