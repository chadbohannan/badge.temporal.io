# Known Cruft, Dead Code, and Drift

A running ledger of things found during ingestion that are real, compiled/shipped, and either inert, misleading, silently lossy, or drifted from their own docs — as opposed to normal working code. Each entry links to the page with the full citation and detail; this page exists so the whole set can be scanned at once rather than rediscovered one wiki page at a time. Entries are grouped by kind, not by discovery date; when re-verifying against a newer commit, update the entry in place rather than appending a duplicate.

## Retired features still executing (not excluded, just inert)

- **`GUIManager`'s `ScreenAccess`/`badgeState` routing** (`ScreenAccess::kPairedOnly`/`kAny`/`kUnpairedOnly`) runs on every screen transition but every reachable branch returns `true`, and no screen anywhere declares the one value (`kUnpairedOnly`) that would ever be blocked. Leftover from a pre-[offline-first](../concepts/offline-first-runtime.md) pairing-gate design. See [the screen stack](../components/gui-screen-stack.md).
- **`verify_badge_ble`** in Ignition's flash worker is a fully implemented, worker-registered Temporal activity that watches serial logs for BLE scan/advertise output — but `BadgeFlashWorkflow` never calls it, hardcoding a synthetic "skipped" result instead. Consistent with BLE being excluded from the public firmware build (below), but the flash-tooling side wasn't deleted to match. See [Ignition flash workflow](../components/ignition-flash-workflow.md).
- **`BadgeDisplay.cpp`'s `renderQR()`/`renderBoop()`/`renderInputTest()`/`renderBoopResult()`** are four fully-implemented legacy render functions, structurally unreachable: they're only ever invoked through `renderScreen()`'s `RenderMode` switch while `badgeDisplayActive` is true, but that window only ever sees `MODE_BOOT` before flipping straight to `MODE_MENU` (and handing the OLED to `GUIManager` for good) — nothing in the tree ever sets `renderMode` to the values these four functions handle. Pre-`GUIManager` code left in place rather than deleted. See [the screen stack](../components/gui-screen-stack.md).
- **`ScheduleData.cpp`'s "MINE" personal-schedule mode** (`ScheduleMode::kPersonal`) is fully modeled — its own label, its own empty-schedule dataset, its own cache path — but `s_mode` is never assigned that value anywhere, and `sched_toggle_mode()` (bound to the Y button) unconditionally forces full-schedule mode and always returns `false`, making the reset/haptic branch that would follow a successful toggle unreachable too. Pressing Y on the schedule screen is currently a no-op. See [Schedule Screen](../components/schedule-screen.md).

## Features excluded from the public build but still in the source tree

- **BLE room presence** (`firmware/src/ble/`) — a complete venue-beacon scanning and advertising system, excluded from `replay2026` at the `build_src_filter` level (`-<ble/>`), gated back in only by `-DBADGE_ENABLE_BLE_PROXIMITY`. Unlike the entries above, call sites that reference it (`screens/MapScreens.cpp`) are cleanly `#ifdef`-guarded rather than left to silently fail. See [BLE room presence](../components/ble-proximity.md).

- **`ScheduleData.cpp`'s live-refresh path** — `sched_start_refresh()`/`sched_ensure_cache_loaded()` only ever read two hardcoded FATFS cache paths (`/schedule_full_v2.msgpack`, `/schedule_your_v2.msgpack`) before falling back to the embedded bundle; nothing in this public repo ever writes either cache path, and `s_refreshInProgress` (which would surface a "SYNC" header status) is declared but never set `true`. The schedule is effectively always the build-time embedded content on a badge built from this tree alone — consistent with `DataCache`'s own stubbed-out `defaultDownloader()`. See [Schedule Screen](../components/schedule-screen.md) and [Data Bundle](../components/data-bundle.md).

## Present in the source tree but not wired into anything

- **`firmware/scripts/upload_dual.py`** overrides PlatformIO's `UPLOADCMD` to flash every detected badge port in parallel via direct `esptool` calls — but it isn't referenced in any `platformio.ini` `extra_scripts` list, so `pio run -t upload` never invokes it. It duplicates, less robustly, what [Ignition's `FlashBadgesWorkflow`](../components/ignition-flash-workflow.md) already does with per-badge retry and verification, which is the likely reason it was superseded in place rather than deleted. See [build and dev scripts](../components/build-and-dev-scripts.md).

- **`pio run -e echo`/`echo-dev`** appears as a build example in 7 files (`firmware/initial_filesystem/apps/README.md`, both on-device API/dev-guide docs, `firmware/micropython/README.md` + its usermod README, both `docs/markdown/*` files) — none of those PlatformIO environments exist; only `replay2026`/`replay2026-expanded` do. (An eighth offender, `firmware/src/doom/README.md`, was deleted along with the rest of the Doom port on 2026-09-17, dropping the count from 8.) See [badge apps](../components/badge-apps.md) and [the public/private scope boundary](../concepts/public-repo-scope-boundary.md).
- **`docs/markdown/badge-api-reference.md` and `badge-developer-guide.md`** are a third, undocumented copy of the app-authoring reference (not linked from `docs/README.md`'s own file list), currently *ahead* of the badge-embedded copy in `firmware/initial_filesystem/docs/` — it documents `oled_screenshot()`, persistent matrix apps, IR Playground modes, and firmware-update/Community-Apps content the on-device docs don't have yet. Unclear whether it's a staging draft or an independently-drifting reference. See [Docs Site](../systems/docs-site.md).

## Silent data loss in a pipeline (no error, just missing output)

- **`floors.md`'s `` `sponsors: ...` `` inline tags** are matched by `build-data.py`'s section regex (so parsing doesn't fail on them) but never captured into a named field — they never reach `floors.json` or the firmware. May be intentional (the booth's free-text description already conveys the same information) or may be an unfinished feature; not resolvable from the source alone. See [Data Bundle](../components/data-bundle.md).

## Past regressions, now fixed, but worth knowing about if touching the same code

These aren't currently broken — they're fixed and cited here only because the failure mode (silent, no crash, no error) is a pattern worth recognizing before making a similar change:

- **`NEC_MAX_WORDS`** was briefly tightened 64→8 when WiFi still handled post-boop sync; once Boops became IR-only, the 8-word ceiling silently dropped large `DATA` frames (encode returns 0, caller skips sending) and peers retransmitted `STREAM_REQ` forever. Restored to 64. See [NEC IR protocol layer](../components/nec-ir-protocol.md).
- **`NEC_RX_SYMBOL_COUNT`** was briefly shrunk to 320 (enough for 8-word frames only), silently truncating any `DATA` frame with more than one TLV once the exchange protocol started batching. Restored to 2112, with a comment tying it to `NEC_MAX_WORDS` so the two get changed together. See [NEC IR protocol layer](../components/nec-ir-protocol.md).
- **`GUIManager::kMaxScreens`** was bumped from 16 after the screen-registration table actually hit that cap and started silently dropping screens past it, with no way for `registerScreen` to report the table was full. See [the screen stack](../components/gui-screen-stack.md).
- **FATFS directory corruption**: concurrent writers (Boops, `BadgeInfo`, `BadgeConfig`, `StartupFiles`, the FileBrowser) racing inside `oofatfs` (built with `FF_FS_REENTRANT=0`) produced JSON body bytes showing up as fake 8.3 directory entries after a heavy write window. Fixed by `Filesystem::IOLock`, a recursive mutex every direct `f_*` call is expected to wrap. See [Storage Model](../components/storage-model.md).
- **`Config`'s settings array**: a too-small `kMaxSettings` silently truncated writes and let out-of-bounds `get()`/`apply()` calls corrupt adjacent `Config` members — surfaced as `log_notify` reading back a huge garbage value and crashing the badge. Fixed with a `static_assert` enforcing `kMaxSettings >= kCount`. See [Storage Model](../components/storage-model.md).
