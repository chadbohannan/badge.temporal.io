# Ignition

Ignition is the Temporal-powered build-and-flash tool at `ignition/`, built to bulk-flash the Replay 2026 badge fleet and equally usable for a single badge on a desk. It runs a local [Temporal](https://temporal.io) server (no cloud dependency) so every flash run is a durable, resumable, browsable workflow rather than a one-shot script — runs are visible in the Temporal Web UI at `http://localhost:8233` while the dev server is up.

## Why a workflow engine for flashing

Flashing many badges in parallel from USB hubs is failure-prone in ways an imperative script handles badly: individual boards drop out mid-write, ports get renumbered when hubs are swapped, and a batch can be interrupted and need to resume without re-flashing boards that already succeeded. Temporal's workflow/activity model gives Ignition per-badge state machines for free: `FlashBadgesWorkflow` detects the currently connected set and starts one child `BadgeFlashWorkflow` per badge, each independently working through `resolve_badge_port -> flash_badge_images -> verify_badge_boot_marker -> sync_badge_clock` with automatic retry. Detailed esptool progress streams through Temporal's activity heartbeat mechanism instead of being crammed into one giant workflow-history payload, which is also why Ignition doesn't need its own separate log-shipping story — `http://localhost:8233/namespaces/default/workflows` is the log.

The "Enter prompt" in `start.sh` (skippable with `-y`) is a deliberate batch boundary: Ignition snapshots whatever badges are connected at that moment and starts child workflows only for that set, so swapping a powered hub mid-batch requires unplugging, connecting the next hub, and re-running Ignition rather than expecting old child workflows to pick up new devices.

The actual Temporal workflow/activity mechanics — the four workflow types, per-badge retry design, USB bootloader recovery, and boot/clock/BLE verification — are covered on the [Ignition flash workflow](../components/ignition-flash-workflow.md) page; this page stays at the "why" level.

## A safety check before spending time on a build

`flash.py --expected-count N` runs a preflight `DetectBadgesWorkflow` before touching the build or flash path at all: if the number of currently-connected badges doesn't match `N`, the whole run refuses to proceed with an explicit error rather than silently building for however many badges happen to be plugged in. This matters most for the bulk-flashing case a workflow engine was chosen for in the first place — a hub with a loose cable dropping one badge shouldn't result in flashing 31 boards and quietly skipping the 32nd without anyone noticing until later.

## Recommended path vs. source builds

`./start.sh --latest-release` is the recommended public flashing path: it downloads `replay2026-factory-16MB.bin` from the latest GitHub Release (see the [release workflow](../components/release-workflow.md)), caches it under `~/.cache/replay2026-badge/releases/`, and flashes it through the same Temporal pipeline as a source build. The download itself happens in `flash.py` before any Temporal workflow starts — it hits the GitHub Releases API directly, skips re-downloading a same-named cached file unless `--force-download` is passed, and `--release-tag` pins to a specific published tag instead of "latest" when reproducing an exact build matters. `--build-and-flash` and the bare `./start.sh` instead invoke PlatformIO (`build_firmware` activity) against `../firmware` and prepare a fresh default filesystem image before flashing — this is the path to use when validating firmware changes rather than the shipped release.

Badges running the normal native-USB-JTAG firmware reset into bootloader automatically over USB serial with no manual boot-button sequence; a badge running older QA firmware whose port instead enumerates as a plain USB-CDC device needs an explicit RTS/DTR reset pulse to drop into bootloader first — see [Ignition flash workflow](../components/ignition-flash-workflow.md) for that recovery path. `IGNITION_UPLOAD_BAUD` overrides the direct esptool upload baud rate (default `921600`, matching the board definitions), and up to 32 badges can flash concurrently.

## The TUI polls the same queries a human could run by hand

`flash.py`'s `Live`-panel display (via `rich`) isn't a separate status channel from the Temporal Web UI — it polls the exact same workflow `describe()`/`query()` calls a person could run against `http://localhost:8233` themselves, once every `POLL_INTERVAL` (0.35 s). `_run_flash()`'s loop queries `FlashBadgesWorkflow.status` and then calls `_query_child_statuses()`, which fans out one `BadgeFlashWorkflow.status` query per child badge concurrently via `asyncio.gather` and merges each child's live phase (`resolving`, `preparing`, `flashing`, `booting`, `verifying_ble`, ...) back into the parent's row for that badge — a query failure on any one child (e.g. it just completed and its handle briefly errors) is swallowed and that row simply keeps its last-known status rather than crashing the whole display. Every workflow `flash.py` starts (`BuildFirmwareWorkflow`, `DetectBadgesWorkflow`, `FlashBadgesWorkflow`) is started with a `memo={"ignition_kind": ...}` and `static_summary`/`static_details`, which is what makes each run identifiable by purpose in the Temporal Web UI's workflow list rather than just by its generated ID. If `Client.connect("localhost:7233")` fails outright, `run()` catches it and prints a pointer to `./start.sh` rather than a raw connection traceback — the one error path that has nothing to do with badges or builds.

## Test coverage: two narrow unit-test files, no integration tests

`ignition/tests/test_flash_device_detection.py` and `test_release_download.py` are the only tests in `ignition/` — both import private (`_`-prefixed) helper functions directly rather than exercising any workflow or activity end-to-end, since doing that would require a running Temporal server and real or emulated USB hardware. The device-detection tests pin down `_looks_like_badge_device()`'s allowlist/denylist behavior (rejecting `/dev/cu.debug-console` and `/dev/cu.Bluetooth-Incoming-Port`, accepting a bare `/dev/cu.usbmodem*` or anything whose `hwid` reports the Espressif USB-JTAG VID/PID `303A:1001`) and `_needs_usb_bootloader_recovery()`'s port-name heuristic — both covered in more depth on [Ignition flash workflow](../components/ignition-flash-workflow.md). The release-download tests cover `flash.py`'s own GitHub Releases helpers (`_github_release_url`, `_select_release_asset`, `_release_cache_path`) with no network calls, including that a missing `replay2026-factory-16MB.bin` asset raises a `RuntimeError` listing what assets *were* available — the same error message path a user hits if `--release-tag` points at a release built before the factory-image asset existed.

## Relationship to the storage model

Ignition's flashing paths map directly onto the three storage tiers described on the [storage model](../components/storage-model.md) page: a firmware-only build+flash never touches FATFS or wipes NVS, while `--factory-image` (a full esptool batch write of bootloader + partition table + firmware + FATFS) wipes on-badge FATFS contents and is why `firmware/scripts/badge_sync.py` exists as the narrower, non-destructive alternative for pushing a handful of changed files after the fact. See the [flashing runbook](../runbooks/flashing-a-badge.md) for which of Ignition's flags to reach for in a given situation.
