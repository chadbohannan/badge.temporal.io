# Replay 2026 Badge Firmware

The badge's on-device software: a PlatformIO/Arduino C++ application for the ESP32-S3, with an embedded MicroPython runtime layered on top for user-facing apps. The public build target is the `replay2026` environment in `firmware/platformio.ini`, targeting board `esp32-s3-devkitc-1-n16r8v` at 240 MHz with the `partitions_replay_16MB_doom.csv` partition table — see the [badge device](../components/badge-device.md) page for what that board actually is (display, LED matrix, IMU, IR, battery) and what the partition table's sizes mean in flash-capacity terms. A second environment, `env:replay2026-expanded`, extends it with a different partition table (`partitions_replay_16MB_ver2.csv`) rather than duplicating the whole env block.

The `[env:replay2026]` block also has to redeclare `board_build.embed_files = ../data/out/bundle.bin` even though it `extends = base`, because PlatformIO does not propagate `embed_files` through `extends` — any environment that builds `src/api/DataCache.cpp` (which references the `_binary_bundle_bin_start`/`_end` symbols) needs its own copy of that line or the link fails. That embedded bundle is the schedule/speaker/floor data produced by the [data bundle pipeline](../components/data-bundle.md).

## Runtime shape

The firmware boots straight into a local UI with no pairing gate and no private backend transport — see [offline-first runtime](../concepts/offline-first-runtime.md) for why that's a deliberate constraint on this public build, not just an absence of a feature. `firmware/src/README.md` is the maintained orientation map over the C++ source tree (`api/`, `boops/`, `hardware/`, `hw/`, `identity/`, `infra/`, `ir/`, `led/`, `messaging/`, `micropython/`, `screens/`, `ui/`); this wiki doesn't re-tabulate that map, only the pieces with enough non-obvious behavior to be worth a dedicated page: the [three-tier storage model](../components/storage-model.md), the [MicroPython bridge](../components/micropython-bridge.md) and the [app-authoring model](../components/badge-apps.md) built on it, [IR-based Boops contact exchange](../components/badge-boops.md), the [ambient LED runtime](../components/led-app-runtime.md), and the [Doom port](../components/doom.md), which is the one app mode that takes over the badge's resources entirely instead of cooperating through the normal MicroPython pump.

Two cores split the work: Core 0 runs the IR task (`irTask`, driving `boops/BoopsProtocol.cpp`'s state machine and the low-level NEC RMT decoders in `hw/`), and Core 1 runs the Arduino `loop()` task — GUI, explicit MicroPython-triggered HTTP, and journal saves — with a 24 KB stack (`SET_LOOP_TASK_STACK_SIZE(24*1024)` in `main.cpp`) sized to leave headroom for MicroPython. While Python code is sleeping or polling, `mpy_service_pump()` (`firmware/src/micropython/ReplayMicropythonAPI.cpp`) keeps inputs, OLED/LED ownership, the mouse overlay, IMU, and haptics responsive.

## Build and flash paths

[Ignition](ignition.md) is the default flashing path and the authoritative compile gate — `firmware/src/README.md` notes that the local `.pio/build/replay2026/` cache has masked header-dependency failures across multiple refactors, so `cd ignition && yes '' | ./start.sh -e replay2026` is the trustworthy build check, not a bare `pio run`. Direct PlatformIO (`pio run -e replay2026`, `-t upload`, `-t uploadfs`) remains a secondary developer path for people already inside the firmware project. `firmware/build.sh replay2026 -n` forces a clean local rebuild for a faster sanity check when Ignition's full pipeline isn't warranted.

Release builds are produced by the [release workflow](../components/release-workflow.md), which is also what the public [Community Apps registry](../components/community-apps-registry.md) is regenerated from. The public `replay2026` build excludes an otherwise-complete [BLE room-presence system](../components/ble-proximity.md) at the source-filter level — one of the clearer signs that this repo's source tree is broader than what actually ships.
